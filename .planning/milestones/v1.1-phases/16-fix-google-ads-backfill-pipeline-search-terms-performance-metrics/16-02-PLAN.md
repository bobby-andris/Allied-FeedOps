<objective>
Optimize the performance and search terms backfill pipeline throughput by parallelizing GAQL chunk queries, eliminating N+1 variant_index lookups, and batching Supabase upserts. Then kill orphaned jobs and restart both backfills with optimized code.

Purpose: Job 2c738140 (performance backfill) was killed at 90/2784 when a code push triggered Cloud Run redeployment. At the pre-optimization rate (~1 SKU/min = ~46 hours), the backfill cannot complete within a single Cloud Run container lifecycle. Three independent bottlenecks compound this slowness: (1) sequential GAQL chunk processing (~25-50s per 10-SKU batch), (2) N+1 variant_index lookups in search terms (~tens of thousands of individual DB queries), and (3) individual Supabase upserts per SKU in performance baselines. Fixing all three cuts end-to-end time by ~5-10x.

Output: Optimized code deployed, orphaned jobs cleaned up, both backfills restarted and running.

## google_ads_performance.py — fetch_batch_product_performance (lines ~297-430)
Already has chunking from 16-01 (OFFER_ID_CHUNK_SIZE=25, _chunks helper).
Current bottleneck: sequential `for chunk in _chunks(safe_ids, OFFER_ID_CHUNK_SIZE)` loop.
Each chunk takes ~2-5s. A 10-SKU batch has ~250 IDs / 25 = 10 chunks = 25-50s sequential.
Fix: Use `concurrent.futures.ThreadPoolExecutor(max_workers=5)` to run chunks in parallel.
Expected: 5 parallel workers × ~2-5s = ~5-10s per batch (5x speedup).

## google_ads_search_terms.py — get_variant_info (lines ~371-420)
Currently does individual Supabase query per offer ID. The `_variant_cache` dict helps for
repeated lookups but first-time lookups are all individual queries.
With ~10,000 search term results × up to 10 variants each = tens of thousands of individual DB queries.
Fix: Add `_preload_variant_cache()` method that bulk-loads ALL variant_index rows (~2,784 × 25 = ~69,600 rows)
into `_variant_cache` in a single paginated Supabase query at the start of `fetch_search_terms`.
Expected: From tens of thousands of queries → 1-7 paginated queries (1000 rows each).

## workers.py — collect_performance_batch (lines ~340-449)
Currently upserts one performance_baselines row per SKU in a for loop (line 426).
Fix: Collect all validated records into a list, then upsert in one batch call.
Expected: From 10 individual upserts → 1 batch upsert per batch (minor speedup, reduces DB round trips).

       ```python
       def _fetch_chunk_data(client, customer_id: str, chunk: list[str], start_date: str, end_date: str) -> list[tuple[str, dict]]:
           """Fetch GAQL data for a single chunk of offer IDs. Returns list of (product_id, row) tuples."""
           ids_clause = ", ".join(f"'{oid}'" for oid in chunk)
           query = f"""
           SELECT
             segments.product_item_id, segments.date,
             campaign.advertising_channel_type,
             metrics.impressions, metrics.clicks, metrics.ctr,
             metrics.conversions, metrics.conversions_value, metrics.cost_micros
           FROM shopping_performance_view
           WHERE segments.product_item_id IN ({ids_clause})
             AND segments.date BETWEEN '{start_date}' AND '{end_date}'
           ORDER BY segments.product_item_id, segments.date
           """
           try:
               rows = _run_gaql_query(client, customer_id, query)
               logger.info("Chunk of %d IDs returned %d rows", len(chunk), len(rows))
               results = []
               for row in rows:
                   product_id = row.get("segments", {}).get("product_item_id", "")
                   if product_id:
                       results.append((product_id, row))
               return results
           except Exception as e:
               logger.error("Failed to fetch chunk of %d IDs: %s", len(chunk), e)
               return []
       ```

    3. Replace the sequential for loop in `fetch_batch_product_performance` with:
       ```python
       MAX_PARALLEL_CHUNKS = 5

       chunks = list(_chunks(safe_ids, OFFER_ID_CHUNK_SIZE))
       logger.info("Processing %d offer IDs in %d chunks (max %d parallel)", len(safe_ids), len(chunks), MAX_PARALLEL_CHUNKS)

       grouped: dict[str, list[dict]] = defaultdict(list)

       with ThreadPoolExecutor(max_workers=MAX_PARALLEL_CHUNKS) as executor:
           futures = {
               executor.submit(_fetch_chunk_data, client, customer_id, chunk, start_date, end_date): i
               for i, chunk in enumerate(chunks)
           }
           for future in as_completed(futures):
               chunk_idx = futures[future]
               try:
                   chunk_results = future.result()
                   for product_id, row in chunk_results:
                       grouped[product_id].append(row)
               except Exception as e:
                   logger.error("Chunk %d raised exception: %s", chunk_idx, e)
       ```

    4. Keep the existing aggregation logic below the loop unchanged.

    **IMPORTANT**: The Google Ads client `search_stream` is thread-safe for separate calls (each creates its own gRPC stream). Do NOT share the same stream across threads. Each chunk call creates its own `search_stream` invocation via `_run_gaql_query`. But the `client` object itself is shared — this is safe because `search_stream` only reads from the client config to create a new stream.

    **Fix B: Bulk pre-load variant_index cache in SearchTermsClient**

    In `src/feedops/integrations/google_ads_search_terms.py`:

    1. Add a new method `_preload_variant_cache`:
       ```python
       def _preload_variant_cache(self) -> int:
           """Bulk-load all variant_index rows into _variant_cache.

           Eliminates N+1 individual Supabase queries during search term processing.
           variant_index has ~69,600 rows — loaded in paginated batches of 1000.

           Returns:
               Number of rows loaded into cache.
           """
           PAGE_SIZE = 1000
           loaded = 0
           offset = 0

           while True:
               result = (
                   self.supabase.table("variant_index")
                   .select("gmc_offer_id, master_sku, finish, finish_code, shopify_variant_id")
                   .range(offset, offset + PAGE_SIZE - 1)
                   .execute()
               )

               if not result.data:
                   break

               for row in result.data:
                   gmc_offer_id = row.get("gmc_offer_id", "")
                   if gmc_offer_id:
                       # Store with lowercase key (consistent with get_variant_info normalization)
                       self._variant_cache[gmc_offer_id.lower()] = {
                           "master_sku": row.get("master_sku"),
                           "finish": row.get("finish"),
                           "finish_code": row.get("finish_code"),
                           "shopify_variant_id": row.get("shopify_variant_id"),
                       }

               loaded += len(result.data)
               offset += PAGE_SIZE

               if len(result.data) < PAGE_SIZE:
                   break

           logger.info(f"Pre-loaded {loaded} variant_index rows into cache")
           return loaded
       ```

    2. Call `_preload_variant_cache()` at the start of `fetch_search_terms`, right after the campaign_products fetch and before the search_term_view loop:
       ```python
       # Pre-load variant_index to eliminate N+1 lookups during search term processing
       if not self._variant_cache:
           self._preload_variant_cache()
       ```

    3. The existing `get_variant_info` method already checks `self._variant_cache` first (line 385-386). With the cache pre-loaded, it will hit the cache for every lookup and never query Supabase individually.
