## Summary

Phase 25.2 must fix a fundamental architectural misalignment: 8 Claude Code skill files (329K chars total) are being dumped raw into GPT-5.2's system prompt, creating a 57K-token prompt with 12 contradictions, conflicting platform rules, and instructions designed for an interactive coding assistant rather than a content generation model. Five previous prompt iterations failed because each was designed by Claude using Claude-optimized patterns without empirical GPT-5.2 testing.

The user has locked a key architectural decision: **separate API calls per platform** with **platform-specific schemas**. This eliminates the root cause of conflicting platform rules (Google vs Bing vs Shopify all in one call). The research question is: what should each platform-specific prompt contain, and how should skill knowledge be integrated?

The Agent Skills specification recommends SKILL.md under 5000 tokens with references/ loaded on demand. Our skills are 5-10x oversized (8K-48K chars each) because they were written as comprehensive Claude Code guidance documents. The valuable domain knowledge (title formulas, finish descriptions, gold examples, brand voice rules, category hooks) must be extracted and restructured as focused, platform-specific prompt sections -- not abandoned.

**Primary recommendation:** Build 3 platform-specific system prompts (Google, Bing, Shopify) each under 8K tokens, extracting relevant knowledge from skills. Implement platform-specific JSON schemas. Generate finish sentences in a separate focused call. Test each change empirically with `scripts/ab_prompt_test.py` against real GPT-5.2 API.

### Pattern 1: Platform-Specific Generation Architecture

**What:** Each platform gets its own API call with dedicated schema, system prompt, and skill subset.

**When to use:** Every content generation call (regeneration, batch, hybrid).

**Architecture per SKU:**
```
Master SKU "1025U" generation:
  Call 1: Google  → google_title, google_short_title, google_description (with {FINISH_NAME}, {FINISH_SENTENCE} placeholders)
  Call 2: Bing    → bing_title, bing_description (with {FINISH_NAME}, {FINISH_SENTENCE} placeholders)
  Call 3: Shopify → shopify_title, shopify_description, shopify_meta_description (finish-agnostic)
  Call 4: Finish  → 28 product-specific finish sentences for variant expansion
```

**Schema design per platform:**

```python
# Google schema (strict mode)
GOOGLE_SCHEMA = {
    "type": "object",
    "properties": {
        "google_title": {"type": "string", "description": "Google Shopping title. MUST start with {FINISH_NAME}. Max 150 chars."},
        "google_short_title": {"type": "string", "description": "Max 70 chars. Product type + key dimension only."},
        "google_description": {"type": "string", "description": "Plain text, 700-900 chars. Include {FINISH_SENTENCE} placeholder where finish context flows naturally."},
        "claims": {"type": "array", "items": {...}},
        "self_score": {"type": "object", "properties": {
            "accuracy": {"type": "integer"},
            "specificity": {"type": "integer"},
            "engagement": {"type": "integer"},
        }},
    },
    "required": [...],
    "additionalProperties": False,
}

# Bing schema -- similar but description targets 700-1000 chars for synonym coverage
# Shopify schema -- HTML allowed, finish-agnostic, no {FINISH_NAME}/{FINISH_SENTENCE}
# Finish sentence schema -- 28 product-specific sentences keyed by finish code
```

**Critical: {FINISH_SENTENCE} mechanism for Google/Bing:**
- The system prompt explicitly defines `{FINISH_SENTENCE}` as a placeholder string
- The schema description instructs: "Include the literal string `{FINISH_SENTENCE}` where finish context flows naturally"
- GPT-5.2 with strict schema will output the literal placeholder
- Variant expansion post-processes: swap `{FINISH_NAME}` and `{FINISH_SENTENCE}` with real values

### Pattern 4: Evidence Handling Without Banning

**What:** User locked: pass ALL evidence, fix the skill/prompt problem, don't band-aid with word banning.

**Root cause of evidence echoing:** GPT-5.2's "conservative grounding bias" causes it to preferentially echo verbatim text from evidence over instructions. When the evidence contains banned words ("finest"), bad grammar ("insure"), or competitor names ("jan barboglio"), GPT-5.2 echoes them despite system prompt prohibitions.

**Approach (per user decision):** With platform-specific calls and properly loaded skill knowledge, GPT-5.2 should receive:
1. Brand voice rules that deeply explain WHY certain language is wrong (not just "don't use X")
2. Positive examples of excellent content (not just prohibitions)
3. Enough context to understand the brand deeply enough to self-regulate

**Fallback if evidence echoing persists after prompt fix:** Consider pre-processing evidence to add metadata flags (e.g., `"source": "manufacturer_copy"`, `"reliability": "raw"`) so GPT-5.2 understands the evidence is source material to transform, not copy.

### Anti-Patterns to Avoid
- **All skills in every call:** The current pattern loads all 8 skills (260K chars) regardless of platform. This creates contradictions and wastes context.
- **Single schema for all platforms:** The current CANDIDATE_SCHEMA requires all fields (Google + Bing + Shopify) in one response. This forces multi-tasking.
- **Claude-optimized prompt patterns:** Priority hierarchies (P0/P1/P2), numbered constraint lists, and detailed "good/bad" examples work for Claude but GPT-5.2 at medium reasoning skims them.
- **Theoretical prompt design without testing:** Every previous iteration was designed theoretically and tested end-to-end. Phase 25.2 must test atomically.

## Common Pitfalls

### Pitfall 1: Over-engineering the prompt before testing
**What goes wrong:** Designing a perfect theoretical prompt, implementing it fully, then discovering GPT-5.2 doesn't follow half the instructions.
**Why it happens:** Each prompt iteration so far was designed by Claude using Claude-optimized patterns and tested end-to-end only.
**How to avoid:** Start with the simplest possible prompt for one platform (Google). Add one constraint at a time. Test each addition with `--sku 1025U`. Only proceed when each constraint is empirically verified.
**Warning signs:** Writing more than 500 chars of prompt without running a test.

### Pitfall 2: Assuming skills work the same way for GPT-5.2 as Claude
**What goes wrong:** Dumping SKILL.md files into GPT-5.2's system prompt and expecting the same comprehension as Claude.
**Why it happens:** The skills were written for Claude Code with Claude-specific patterns (interactive guidance, "you the AI assistant", cross-skill references).
**How to avoid:** Extract actionable knowledge from skills. Format it as concise, imperative instructions. Test format effectiveness empirically.
**Warning signs:** System prompt exceeding 10K tokens per platform call.

### Pitfall 3: Not testing {FINISH_SENTENCE} placeholder mechanism
**What goes wrong:** GPT-5.2 interprets "include finish context" as "describe the finish" instead of outputting a literal `{FINISH_SENTENCE}` placeholder.
**Why it happens:** The model tries to be helpful and expand placeholders rather than preserve them literally.
**How to avoid:** Explicit schema description: "Output the literal string `{FINISH_SENTENCE}` -- do NOT expand this placeholder." Test this FIRST before building the rest of the prompt.
**Warning signs:** Generated descriptions containing "Finished in Satin Brass." instead of `{FINISH_SENTENCE}`.

### Pitfall 4: Breaking prompt caching with per-platform system prompts
**What goes wrong:** 3 different system prompts = 3 separate cache entries. If prompts change between requests, cache hit rate drops.
**Why it happens:** Each platform has a different system prompt prefix.
**How to avoid:** Structure system prompts with a shared prefix (brand voice, accuracy rules) followed by platform-specific suffix. The shared prefix caches across all platforms. Alternatively, accept 3 separate caches since each platform's system prompt will be reused across all SKUs in a batch.
**Warning signs:** 0% cache hit rate in batch runs (check `_extract_usage` in `openai_provider.py`).

### Pitfall 5: Regression in existing pipeline behavior
**What goes wrong:** Refactoring breaks batch generation, hybrid generation, or the regeneration endpoint.
**Why it happens:** `get_system_prompt()` is called from 8+ locations. Changing its signature or behavior has cascading effects.
**How to avoid:** Add platform-specific functions alongside existing ones. Use feature flags. Don't remove the old code path until the new one is validated.
**Warning signs:** Any of these callers breaking: `generator.py:build_split_prompt`, `generator.py:build_variant_prompt`, `main.py:/regenerate`, `main.py:/optimize-sku`, `hybrid_generation.py`.

### Extended Test Harness for Per-Platform Testing

```python
# Source: Extension of scripts/ab_prompt_test.py
# Add per-platform generation support

async def generate_per_platform(
    client: AsyncOpenAI,
    system_prompt: str,
    user_prompt: str,
    schema: dict,
    model: str = "gpt-5.2",
    reasoning_effort: str = "medium",
) -> tuple[dict | None, dict]:
    """Generate content for a single platform with dedicated schema."""
    strict_schema = _make_strict(schema)
    response_format = {
        "type": "json_schema",
        "json_schema": {"name": "platform_content", "strict": True, "schema": strict_schema},
    }
    response = await client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt},
        ],
        response_format=response_format,
        reasoning_effort=reasoning_effort,
        max_completion_tokens=4000,
    )
    content = response.choices[0].message.content
    return json.loads(content), extract_usage(response)
```

## GPT-5.2 API Parameters (Verified Against OpenAI Docs)

### Verified Facts (HIGH confidence)

1. **reasoning_effort and temperature are mutually exclusive** -- Our code already handles this correctly (`openai_provider.py` lines 186-194). When `reasoning_effort` is set, temperature is omitted. When not set, temperature=0.7 is used.

2. **`prompt_cache_retention: "24h"` is already implemented** -- `openai_provider.py` passes `extra_body={"prompt_cache_retention": "24h"}` on every call. GPT-5.2 supports this for extended caching.

3. **Strict `json_schema` mode is already implemented** -- `_build_strict_schema()` adds `additionalProperties: false` and ensures all properties are required. The schema is precomputed at import time.

4. **reasoning_effort defaults to `none` on GPT-5.2** -- Unlike GPT-5 which defaults to `medium`. Our code sets it from `FEEDOPS_REASONING_EFFORT` env var. If unset, no reasoning_effort param is sent (effectively `none`).

5. **Self-reflection improves constraint adherence** -- GPT-5 troubleshooting guide recommends "encouraging the model to self reflect and score its own responses via prompting" and "construct an internal rubric and apply it to the solution before responding." Our self_score field partially does this, but could be leveraged more explicitly.

### Recommendations for API Parameters

| Parameter | Current | Recommended | Rationale |
|-----------|---------|-------------|-----------|
| `reasoning_effort` | From env var (often unset = none) | `"medium"` hardcoded for content gen | Content quality requires reasoning; `none` produces shallow output |
| `max_completion_tokens` | 2000 | 4000 per platform call | Single-platform responses need less than all-platform, but need buffer for descriptions |
| `temperature` | 0.7 (when no reasoning) | Omit (use reasoning_effort instead) | reasoning_effort=medium produces better quality than temperature tuning |
| `text.verbosity` | Not set | Not needed with reasoning_effort | Only relevant when reasoning_effort=none; we'll use medium |

### Open Question: text.verbosity Parameter

The existing research (`docs/research/gpt52-best-practices.md`) mentions `text.verbosity` as a GPT-5.2 parameter. However, the current OpenAI SDK integration uses the Chat Completions API which may not support this parameter directly. The Responses API may be needed. **Recommendation:** Test without `text.verbosity` first. If descriptions are consistently too short, investigate.

## Open Questions

1. **Does GPT-5.2 preserve literal placeholder strings like `{FINISH_SENTENCE}`?**
   - What we know: Previous tests showed GPT-5.2 expanding placeholders instead of preserving them. The schema description can instruct literal preservation.
   - What's unclear: Whether strict schema descriptions alone are sufficient, or if additional system prompt emphasis is needed.
   - Recommendation: Test this FIRST with a minimal prompt. If GPT-5.2 won't preserve placeholders, fall back to generating finish sentences separately and splicing them in post-processing (which is the user's preferred architecture anyway).

2. **What reasoning_effort level produces optimal content quality?**
   - What we know: `medium` was used in Phase 25.1 A/B tests. GPT-5.2 at medium "skims constraint lists" (per root cause analysis). The troubleshooting guide recommends trying `high` if `medium` underthinks.
   - What's unclear: Whether `high` justifies the cost increase for content generation (not a reasoning task).
   - Recommendation: Test `medium` first with the simplified per-platform prompt. If constraint adherence is still poor, test `high` for comparison.

3. **Should finish sentences be generated in the same Google/Bing call or a separate call?**
   - What we know: User wants 28 product-specific finish sentences per SKU. User's discretion says "research decides."
   - What's unclear: Whether generating 28 sentences + a description in one call overloads GPT-5.2, or whether a separate focused call produces better finish sentences.
   - Recommendation: Separate call. The finish sentence task is qualitatively different (28 short creative sentences requiring finish-product pairing knowledge) from the description task (1 long description requiring platform rules + evidence grounding).

4. **How much skill knowledge is too much vs too little?**
   - What we know: 260K chars (all skills) is too much. 6.4K chars (no skills, just SYSTEM_PROMPT) produced lower quality in A/B tests.
   - What's unclear: The optimal amount per platform.
   - Recommendation: Start with minimal extracted knowledge (~3-5K per platform), validate quality, add more if needed. The user explicitly said "research both format effectiveness and content relevance."
