## Mismatch Analysis: Raw Model Output vs Runtime-Normalized Output

### Normalization Pipeline (ALIGNED between runtime and test harness)

The test harness (`ab_prompt_test.py:586-643`) calls `normalize_payload_for_runtime()` which imports and applies the **exact same functions** from `generator.py`:
- `_align_subtype_terms()`
- `_remove_banned_words()`
- `_ensure_finish_placeholder_title()`
- `_ensure_collection_keyword_in_title()`
- `_sanitize_platform_description()`
- `_trim_google_short_title()`

**Verdict: Runtime and test harness normalization are aligned.** This is correct.

### Schema Parsing Path vs Downstream Validation

| Aspect | Runtime (generator.py) | Test Harness (ab_prompt_test.py) |
|--------|----------------------|--------------------------------|
| Schema enforcement | `_build_strict_schema()` in openai_provider.py | `build_response_format()` (identical logic) |
| JSON parsing | `_parse_json_payload()` in openai_provider.py | `parse_json_payload()` (identical logic) |
| Post-parse normalization | `generate_per_platform()` lines 697-757 | `normalize_payload_for_runtime()` |
| Constraint checks | None (runtime doesn't validate) | `evaluate_platform_output()` with HARD/ADVISORY distinction |

**Key finding:** Runtime does NOT validate constraints after normalization — it applies normalization and trusts the result. The test harness validates AFTER normalization, which is the correct architecture (normalization fixes known issues, validation catches remaining gaps).
