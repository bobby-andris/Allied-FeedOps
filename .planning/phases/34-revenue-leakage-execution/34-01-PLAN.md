## Goal
Ensure `routing_recommendations` table exists in production with a unique constraint on `(search_term, custom_label_0)` for upsert support, and build the CRUD API route that handles approve, reject, undo, batch-approve, and history queries. This is the data foundation that all UI work in waves 2-3 depends on.

## Context
- The `routing_recommendations` table schema is defined in `033b_DEFERRED_optimization_control_plane.sql` but may or may not exist in production (033b was labeled DEFERRED; migration 037 only cherry-picked `query_value_scores`).
- The existing `recommendations/route.ts` is a GET-only endpoint that builds a recommendation queue from scoring data. We need to add POST handling for approve/reject/undo/batch while preserving the existing GET.
- The table has check constraints: `recommended_action in ('global_block', 'competitor', 'branded', 'funnel')`, `review_status in ('pending', 'accepted', 'rejected', 'expired')`.
- Upsert requires a unique constraint on `(search_term, custom_label_0)` which does NOT exist in the 033b migration.

## must_haves
- [ ] Migration 039 creates `routing_recommendations` table (IF NOT EXISTS) with the unique constraint on `(search_term, custom_label_0)`
- [ ] API route handles `POST` with actions: `approve`, `reject`, `undo`, `batch_approve`
- [ ] Approve upserts with `review_status='accepted'`, `accepted=true`, `accepted_at`, `accepted_by`
- [ ] Reject upserts with `review_status='rejected'`, optional `rejection_reason` in metadata
- [ ] Undo updates `review_status='pending'`, `accepted=false`, `accepted_at=null`, appends undo to metadata history
- [ ] Batch approve accepts array of terms, filters by confidence > 0.80, upserts all in one call
- [ ] GET endpoint `/api/shopping-funnel/recommendations?action=history` returns recent accepted/rejected recommendations grouped for history view
- [ ] `npm run build` passes

## Tasks

<task id="34-01-01" title="Create migration 039 for routing_recommendations" autonomous="true">
### What
Create `supabase/migrations/039_routing_recommendations_table.sql` that:
1. Creates the `routing_recommendations` table using `CREATE TABLE IF NOT EXISTS` with the exact schema from 033b:
   - `id uuid primary key default gen_random_uuid()`
   - `search_term text not null`
   - `custom_label_0 text not null`
   - `recommended_action text not null`
   - `recommended_tier text`
   - `reason_codes text[] not null default '{}'`
   - `confidence numeric(5,4) not null default 0`
   - `review_status text not null default 'pending'`
   - `accepted boolean`
   - `accepted_at timestamptz`
   - `accepted_by text`
   - `metadata jsonb not null default '{}'::jsonb`
   - `created_at timestamptz not null default now()`
2. Adds check constraints (idempotent DO $$ blocks) for `recommended_action`, `recommended_tier`, `review_status` — copy exactly from 033b.
3. Adds a UNIQUE constraint on `(search_term, custom_label_0)` — this is NEW and not in 033b:
   ```sql
   do $$
   begin
     if not exists (
       select 1 from pg_constraint
       where conname = 'routing_recommendations_term_label_unique'
     ) then
       alter table routing_recommendations
         add constraint routing_recommendations_term_label_unique
         unique (search_term, custom_label_0);
     end if;
   end $$;
   ```
4. Creates indexes (IF NOT EXISTS) from 033b.
5. Enables RLS + permissive policy (same pattern as 033b).

### Why
Upsert on `(search_term, custom_label_0)` requires a unique constraint. The 033b migration only has indexes, not a unique constraint. Using `CREATE TABLE IF NOT EXISTS` makes this safe regardless of whether 033b was applied.

<task id="34-01-02" title="Build CRUD API route for recommendations" autonomous="true">
### What
Rewrite `dashboard/src/app/api/shopping-funnel/recommendations/route.ts` to support both the existing GET behavior and new POST operations.

**Preserve existing GET** — keep the current logic that calls `getNeedsDecisionTerms` + `buildRecommendationQueue`.

**Add GET with `?action=history`** — when `action=history` query param is present:
```typescript
// Query routing_recommendations for accepted/rejected items
const { data, error } = await supabase
  .from('routing_recommendations')
  .select('*')
  .in('review_status', ['accepted', 'rejected'])
  .order('accepted_at', { ascending: false, nullsFirst: false })
  .order('created_at', { ascending: false })
  .limit(200)

// Return with day grouping info (client does actual grouping)
return NextResponse.json({ history: data })
```

**Add GET with `?action=statuses`** — load current recommendation statuses for overlay:
```typescript
const { data } = await supabase
  .from('routing_recommendations')
  .select('search_term, custom_label_0, review_status, accepted_at, accepted_by, metadata')
  .order('created_at', { ascending: false })

return NextResponse.json({ statuses: data })
```

**Add POST handler** with body `{ action, ...payload }`:

1. **`action: 'approve'`** — Upsert single term:
   ```typescript
   {
     action: 'approve',
     searchTerm: string,
     customLabel0: string,
     recommendedTier: string,
     currentTier: string,
     confidence: number,
     impact: { low: number, mid: number, high: number },
     recommendedAction?: string  // optional override, defaults to 'funnel'
   }
   ```
   Upsert to `routing_recommendations` with `review_status='accepted'`, `accepted=true`, `accepted_at=now()`, `accepted_by='operator'`, `recommended_action` from payload (default `'funnel'`; use `'global_block'` for wasted spend Block actions per LEAK-03). The `recommended_action` check constraint allows: `('global_block', 'competitor', 'branded', 'funnel')`. Store `currentTier` and `impact` in `metadata` JSONB. Append to `metadata.history` array: `{ action: 'approved', at: ISO string }`.

2. **`action: 'reject'`** — Upsert single term:
   ```typescript
   {
     action: 'reject',
     searchTerm: string,
     customLabel0: string,
     reason?: string  // optional rejection reason
   }
   ```
   Upsert with `review_status='rejected'`, `accepted=false`. If `reason` provided, store in `metadata.rejection_reason`.

3. **`action: 'undo'`** — Update existing:
   ```typescript
   {
     action: 'undo',
     searchTerm: string,
     customLabel0: string
   }
   ```
   Update (not upsert): set `review_status='pending'`, `accepted=false`, `accepted_at=null`, `accepted_by=null`. Append to `metadata.history`: `{ action: 'undone', at: ISO string }`.

4. **`action: 'batch_approve'`** — Upsert array:
   ```typescript
   {
     action: 'batch_approve',
     terms: Array<{
       searchTerm: string,
       customLabel0: string,
       recommendedTier: string,
       currentTier: string,
       confidence: number,
       impact: { low: number, mid: number, high: number }
     }>
   }
   ```
   Map to rows and upsert all at once with `onConflict: 'search_term,custom_label_0'`.

**Use `createAdminClient`** for all Supabase operations (service role needed for upserts through RLS).

Import pattern:
```typescript
import { createAdminClient } from '@/lib/supabase/admin'
```

### Why
This single API route handles all CRUD operations for the approval workflow. Keeping it in the existing `recommendations/route.ts` file keeps the API surface clean.

Build must pass. The route should export both GET and POST. The `recommendedAction` field must be accepted in the approve payload.
</task>
