## Summary

The current prompt architecture suffers from a fundamental structural problem: **260,776 characters (~67K tokens) of skill content injected into the system prompt**, creating massive over-instruction that directly triggers GPT-5.2's known failure modes. After 3 rounds of evaluation producing keyword-stuffed, monotonous, filler-heavy content, the evidence points to architectural anti-patterns rather than missing rules.

The GPT-5.2 prompting guide explicitly warns that over-instruction causes repetitive, generic output -- the model follows instructions so literally that contradictory guidance between 8 skills produces a lowest-common-denominator blend of all instructions. The current prompt contains at least 12 direct contradictions between skills, multiple redundant instructions on the same topics (competitor positioning alone appears in 4 separate places), and embeds Claude Code documentation (skill metadata, agent instructions) that is irrelevant noise to GPT-5.2.

**Primary recommendation:** Replace the 8 SKILL.md injections (260K chars) with a single, purpose-built GPT-5.2 prompt under 15K characters that distills the essential guidance into non-contradictory, hierarchical instructions following the CTCO framework (Context, Task, Constraints, Output). Use YAML configs (~5K chars total) as the distilled injection source rather than full SKILL.md files which were designed for Claude Code, not GPT-5.2.

### Pattern 1: CTCO Framework for GPT-5.2
**What:** Structure prompts as Context -> Task -> Constraints -> Output
**When to use:** All GPT-5.2 prompts
**Why:** GPT-5.2 prompting guide explicitly recommends this. "Miss one, and quality drops." The model follows this structure more reliably than free-form instructions.

```
<context>
You write Google Shopping, Bing Shopping, and Shopify product content for Allied Brass,
a direct-to-consumer solid brass bathroom hardware manufacturer.
</context>

<task>
Generate optimized titles and descriptions for MasterSKU: {master_sku}.
Use ONLY information from the evidence table below. Every factual claim must be traceable.
</task>

<constraints>
[Hierarchical, non-contradictory rules organized by priority]
</constraints>

<output>
Return valid JSON matching the provided schema.
</output>
```

### Pattern 2: Hierarchical Constraint Organization
**What:** Replace flat skill dumps with prioritized, non-redundant constraint sections
**When to use:** The constraints section of the CTCO prompt
**Why:** GPT-5.2 follows instructions literally. Contradictions between skills produce averaging behavior (generic output). Priority order resolves conflicts.

```xml
<constraints>
<accuracy priority="P0">
[Non-negotiable factual rules — takes precedence over everything]
</accuracy>

<content_rules priority="P1">
[What to include, what to exclude, length targets]
</content_rules>

<voice_and_style priority="P2">
[Brand voice, tone, banned words — defers to P0/P1 on conflicts]
</voice_and_style>

<platform_specific priority="P3">
[Google/Bing/Shopify format rules]
</platform_specific>
</constraints>
```

### Pattern 3: Distilled Skill Injection via YAML
**What:** Instead of 260K chars of SKILL.md files, inject ~5K chars from YAML configs
**When to use:** For runtime GPT-5.2 prompts
**Why:** YAML configs are already purpose-built distillations of skill knowledge for LLM consumption. SKILL.md files contain Claude Code metadata, agent instructions, rule file references, and workflow guidance irrelevant to GPT-5.2.

### Anti-Patterns to Avoid

- **Over-instruction (CRITICAL):** The #1 anti-pattern. 260K chars of instructions causes GPT-5.2 to produce averaged, generic output. The GPT-5.2 guide warns: "If your instructions are sloppy, it defaults to safe, generic, low-effort output." Contradictory over-instruction is worse than sloppy -- the model tries to satisfy all 8 skills simultaneously and produces the bland intersection of all of them.

- **Contradictory instructions:** Skill A says "mention 28 finishes as a differentiator"; SYSTEM_PROMPT says "do NOT mention 28 finishes." The model either picks one randomly or produces awkward compromises. Every contradiction must be resolved to a single authoritative instruction.

- **Claude-specific content in GPT-5.2 prompts:** SKILL.md files contain `## When to Invoke`, `## Agent Guidance`, `## Rule Files` -- metadata for Claude Code, not GPT-5.2. This is pure noise that wastes tokens and confuses the model's instruction hierarchy.

- **Repeated instructions across skills:** "Solid brass vs die-cast zinc" appears in brand_voice.yaml, shopping_intelligence.yaml, storytelling_patterns.yaml, AND SYSTEM_PROMPT. Four repetitions of the same instruction with slight variations cause the model to over-weight this topic -- producing the keyword-stuffed competitor material references both evaluators rejected.

- **Gold examples in user message:** Examples should be in the system prompt for caching. Moving them to the user message breaks the cacheable prefix and forces re-processing on every SKU.

## External Research Findings

### GPT-5.2 Prompting Best Practices (HIGH confidence)

**Source:** [OpenAI GPT-5.2 Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-2_prompting_guide)

1. **CTCO Framework:** Context -> Task -> Constraints -> Output. "Miss one, and quality drops." GPT-5.2 favors structured architectural prompting over conversational nuances.

2. **Over-instruction is counterproductive:** "Remove 'Take a deep breath' or 'You are a world-class expert.' GPT-5.2 finds this noise." GPT-5.2 is LESS forgiving than earlier models -- sloppy instructions yield safe, generic output.

3. **Ambiguity is a bug:** "Ambiguity is now a bug, not a feature." Precision and clarity are prioritized. Vague rules ("target 600-800") underperform explicit constraints ("MUST be 700-900 characters").

4. **Scope discipline:** "Implement EXACTLY and ONLY what the user requests. No extra features, no added components." For content generation: generate exactly what was asked, no filler.

5. **Concrete verbosity control:** Use "3-6 sentences" or "<=5 tagged bullets" instead of vague character ranges. Or use `text.verbosity` parameter when reasoning_effort is enabled.

6. **XML tags for section delineation:** Use semantically named blocks like `<output_verbosity_spec>`, `<constraints>`. This improves parsing fidelity over `===` delimiters.

7. **Verification steps:** "Re-scan outputs for unstated assumptions." The self_score in our schema serves this purpose -- keep it.

### Google Shopping Description Optimization (MEDIUM confidence)

**Sources:** [AdNabu Guide](https://blog.adnabu.com/google-shopping-feed/google-shopping-feed-description/), [Google Merchant Center Help](https://support.google.com/merchants/answer/6324415?hl=en-GB)

1. **Optimal description length:** 500-1,000 characters. Google indexes full text for query matching. First 160-500 characters most important (displayed in Shopping ads).

2. **What to exclude from descriptions:** Competitor comparisons, promotional content, excessive capitalization, product categories, store links. This aligns with Robert's feedback -- no competitor material names.

3. **Title optimization:** Use all 150 characters. Product type in first 30 chars. Key dimension before char 70. Users see first 70 characters depending on screen size. Separators (|, -, /) enhance readability.

4. **Structured title/description:** For AI-generated content, use `structured_title` and `structured_description` attributes with `digital_source_type=trained_algorithmic_media`. Already implemented in the publishing pipeline.

5. **Keyword strategy:** Add keywords that couldn't fit in the title. Use natural integration, never stuffing. One synonym per natural sentence.

### Competitor Placement Analysis (from CONTEXT.md problem statement)

Bobby's core question: "Why does a competitor get 15-20 placements on a page while we get 1-2?"

The answer lies in Google's auction matching, not content quality alone:
- **Title relevance:** Each unique title variation enters a separate auction. "Polished Chrome Towel Bar" and "Chrome Bathroom Towel Rack" enter different auctions.
- **Keyword coverage:** Competitors with 15-20 placements have listings that match more search term variations through synonym coverage in descriptions.
- **Structured data completeness:** Attribute completeness (size, color, material, pattern) unlocks more eligible impressions.
- **Variant-specific content:** Each finish variant is a separate listing -- optimizing each variant's title for different search terms multiplies placements.

**Implication for prompt architecture:** The prompt should prioritize keyword VARIETY (different synonyms across title + description) over keyword DENSITY (repeating the same terms). The current architecture over-instructs on keyword inclusion, producing stuffing rather than distribution.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Prompt contradiction detection | Manual audit each time | Automated prompt linter script | Skills evolve; contradictions creep back |
| A/B prompt comparison | Manual side-by-side reading | Structured eval framework with blind scoring | Human bias when you know which prompt is which |
| Token counting | Character count / 4 estimate | `tiktoken` library with `o200k_base` encoding | GPT-5.2 uses a different tokenizer; character estimates are ~15% off |
| Prompt assembly | String concatenation in multiple files | Single `build_prompt()` function | Current architecture has 3 prompt assembly paths (generator.py legacy, generator.py split, prompt_builder.py) -- must converge |

**Key insight:** The current architecture has prompt assembly logic in 3 places: `generator.py:build_prompt()` (legacy), `generator.py:build_split_prompt()`, and `prompt_builder.py:build_core_prompt()`. These produce structurally different prompts. The Phase 25.1 rewrite should converge all paths through a single assembly function.

## Common Pitfalls

### Pitfall 1: Surgical Edits Instead of Rethink
**What goes wrong:** Adding more rules to fix specific failures (Round 2: "don't say die-cast zinc", Round 3: "don't include weight capacity") while the structural problem (260K over-instruction) remains.
**Why it happens:** Each evaluation failure looks like a missing rule. But the root cause is too MANY rules that contradict.
**How to avoid:** Start from blank slate. Build new prompt from CTCO framework. Only add rules that pass the contradiction test.
**Warning signs:** Each round adds prohibitions but quality plateaus; descriptions avoid prohibited terms but new generic patterns emerge.

### Pitfall 2: Testing on Training Set
**What goes wrong:** Optimizing the prompt on the 10 evaluation SKUs, then declaring success because those 10 score well.
**Why it happens:** The prompt becomes overfit to the specific failure modes of those 10 SKUs.
**How to avoid:** CONTEXT.md specifies testing on "unseen" SKUs not in the evaluation set. Use 3 representative + 3-5 random unseen.
**Warning signs:** Test SKUs score 85+ but random SKUs score 70-.

### Pitfall 3: Optimizing for Score Instead of Quality
**What goes wrong:** The self_score rubric is in the prompt. The model learns to generate content that scores well on the rubric rather than content that converts shoppers.
**Why it happens:** GPT-5.2 literally follows the scoring rubric instructions and optimizes its output to match.
**How to avoid:** Remove or simplify the scoring rubric in the generation prompt. Use a SEPARATE evaluation prompt (or separate API call) for scoring.
**Warning signs:** Self-scores are consistently 85+ but human evaluators still find content generic or stuffed.

### Pitfall 4: Keeping SKILL.md Injection
**What goes wrong:** Reducing prompt size by removing some skills but keeping others as full SKILL.md files.
**Why it happens:** Attachment to the "rich context" the skills provide.
**How to avoid:** Replace ALL SKILL.md injection with purpose-built GPT-5.2 prompt sections. SKILL.md files remain valuable for Claude Code workflows.
**Warning signs:** System prompt still over 50K chars; skill content still contains Claude-specific metadata.

### Pitfall 5: Not Separating Generation from Evaluation
**What goes wrong:** The generation prompt includes the full quality rubric (10 criteria with weights). The model optimizes for the rubric rather than the shopper.
**Why it happens:** The rubric was designed for human/Claude evaluation but is embedded in the generation prompt for self-scoring.
**How to avoid:** Minimize rubric in generation prompt to 2-3 high-level principles. Keep detailed rubric for a separate evaluation pass.
**Warning signs:** Generated descriptions feel formulaic -- they check boxes rather than telling stories.

## Open Questions

1. **Token counting accuracy**
   - What we know: Character estimates (~4 chars/token) are approximate. GPT-5.2 uses `o200k_base` tokenizer.
   - What's unclear: Exact token count of the current full prompt (system + user) for a real SKU.
   - Recommendation: Use `tiktoken` with `o200k_base` to get exact counts during prompt dump in Track 1.

2. **Metaprompting potential**
   - What we know: The GPT-5.2 guide mentions metaprompting as a technique. Some practitioners use GPT-5.2 to generate its own optimized prompts.
   - What's unclear: Whether metaprompting for ecommerce content produces better results than expert-crafted prompts.
   - Recommendation: This is at Claude's discretion per CONTEXT.md. Consider as an optional experiment if time allows, but don't depend on it.

3. **Reasoning effort sweet spot for content generation**
   - What we know: `reasoning_effort=medium` is the general recommendation. Higher effort = better quality but more cost/latency.
   - What's unclear: Whether `medium` vs `high` produces meaningfully different content quality for product descriptions (not coding/math where reasoning clearly helps).
   - Recommendation: Test `medium` in A/B comparison. If quality plateau, don't escalate to `high` for cost reasons.

4. **Self-score in generation prompt vs separate evaluation**
   - What we know: The self_score schema forces the model to evaluate its own output. This may cause it to optimize for scores rather than quality.
   - What's unclear: Whether removing self_score from generation degrades output quality (it may serve as a useful forcing function for the model to think about quality criteria).
   - Recommendation: Test a variant WITHOUT self_score in the A/B comparison. The generation prompt should focus on generation; evaluation can be a separate pass.

5. **Caching implications of prompt restructure**
   - What we know: Smaller system prompt means less to cache, but the cached prefix is more stable. OpenAI caches the longest common prefix.
   - What's unclear: Whether a 15K system prompt vs 267K system prompt has different cache hit rates in practice.
   - Recommendation: The 15K prompt will cache MORE effectively because it's more likely to be byte-for-byte identical across requests (no dynamic skill loading edge cases).
