**GAP 1 — Fix: `src/feedops/api/performance_baseline.py` wrong divisor**

In `_capture_google_baseline()` (around line 282), the aggregation loop tracks `variants_with_data` (number of variants with impressions > 0). The current code divides totals by this variant count to produce per-variant averages, but the stored column is supposed to hold daily averages (total / days in window). Fix both lines:

```python
# BEFORE (wrong — per-variant average, not daily average)
avg_impressions = total_impressions / variants_with_data
avg_clicks = total_clicks / variants_with_data

# AFTER (correct — daily average over the lookback period)
days_lookback = (datetime.strptime(end_date, "%Y-%m-%d") - datetime.strptime(start_date, "%Y-%m-%d")).days
avg_impressions = total_impressions / days_lookback
avg_clicks = total_clicks / days_lookback
```

Note: `start_date` and `end_date` are already available as string parameters in `_capture_google_baseline`. The `datetime` import already exists at the top of the file. Keep `avg_ctr` and `avg_cvr` unchanged — they are rate calculations, not averages over time.

**GAP 4 — Fix: `dashboard/src/app/api/performance/route.ts` SKU detail queries by null master_sku**

Current code (around line 334-338):
```typescript
const { data: searchQueryRows } = await supabase
  .from('search_queries')
  .select('gmc_offer_id, finish, finish_code, query_text, impressions, clicks, ctr')
  .eq('master_sku', sku)
```

This returns zero rows for any SKU whose search_queries rows were synced with `master_sku=null` (historical data before the lowercase fix). Instead, look up the SKU's gmc_offer_ids from `variant_index` first, then query `search_queries` by offer ID:

```typescript
// Step 1: Get all gmc_offer_ids for this master_sku from variant_index
const { data: variantRows } = await supabase
  .from('variant_index')
  .select('gmc_offer_id, finish, finish_code')
  .eq('master_sku', sku)

const offerIds = (variantRows || [])
  .map(v => v.gmc_offer_id)
  .filter(Boolean)

// Also build finish/finish_code lookup by offer_id for enrichment
const offerFinishMap = new Map<string, { finish: string | null; finish_code: string | null }>()
for (const v of variantRows || []) {
  if (v.gmc_offer_id) {
    offerFinishMap.set(v.gmc_offer_id, { finish: v.finish ?? null, finish_code: v.finish_code ?? null })
  }
}

// Step 2: Query search_queries by gmc_offer_id (resilient to null master_sku in historical rows)
// variant_index stores lowercase shopify_us_ but search_queries stores uppercase shopify_US_
// (written by the dedup block in google_ads_search_terms.py which transforms to uppercase before upsert)
const upperOfferIds = offerIds.map(id => id.replace('shopify_us_', 'shopify_US_'))

const { data: searchQueryRows } = offerIds.length > 0
  ? await supabase
      .from('search_queries')
      .select('gmc_offer_id, finish, finish_code, query_text, impressions, clicks, ctr')
      .in('gmc_offer_id', upperOfferIds)
  : { data: [] }
```

After this change, the existing loop over `rows` (variant grouping by `gmc_offer_id`, search term grouping) continues unchanged. The finish/finish_code on each row will populate correctly since `search_queries` stores them per row. If a row's `finish` is null (historical), enrich it from `offerFinishMap` by matching `row.gmc_offer_id` (case-insensitive). Add this enrichment inside the existing `for (const row of rows)` loop:

```typescript
// Enrich finish from variant_index if missing on the search_queries row
if (!row.finish || !row.finish_code) {
  const offerKey = offerFinishMap.get(row.gmc_offer_id) || offerFinishMap.get(row.gmc_offer_id?.toLowerCase())
  if (offerKey) {
    row.finish = row.finish || offerKey.finish
    row.finish_code = row.finish_code || offerKey.finish_code
  }
}
```

No changes needed to the variant grouping logic or topSearchTerms logic — they already work correctly given properly populated rows.

**GAP 4 (Python side) — Fix: `google_ads_search_terms.py` case-sensitive gmc_offer_id lookup**

In `get_variant_info()` (around line 387), the lookup uses the raw `gmc_offer_id` from Google Ads (which comes back as uppercase `shopify_US_`). The DB stores lowercase `shopify_us_`. Fix by lowercasing before lookup:

```python
# BEFORE
result = (
    self.supabase.table("variant_index")
    .select("master_sku, finish, finish_code, shopify_variant_id")
    .eq("gmc_offer_id", gmc_offer_id)
    .limit(1)
    .execute()
)

# AFTER — lowercase the incoming ID to match DB storage format
result = (
    self.supabase.table("variant_index")
    .select("master_sku, finish, finish_code, shopify_variant_id")
    .eq("gmc_offer_id", gmc_offer_id.lower())
    .limit(1)
    .execute()
)
```

Also lowercase the gmc_offer_id before the cache key lookup and the fallback shopify_variant_id parse, so caching is consistent:

```python
# At the top of get_variant_info, normalize before any use:
gmc_offer_id = gmc_offer_id.lower() if gmc_offer_id else gmc_offer_id
```

This is a forward-looking fix — historical search_queries rows with `master_sku=null` are handled by the route.ts offer-ID-based query from Task 1. Do NOT attempt to backfill the null master_sku values; the route.ts fix is the resilient approach.
