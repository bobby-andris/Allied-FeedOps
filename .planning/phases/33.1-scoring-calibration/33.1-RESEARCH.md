# Phase 33.1: Scoring Calibration - Research

**Researched:** 2026-02-25
**Domain:** Statistical scoring calibration, impact estimation, UX language for intuition-based tiers
**Confidence:** HIGH

## Summary

Phase 33.1 addresses two distinct bugs and a UX reframing need in the tier scoring engine built in Phase 33. The root causes are clearly identifiable in the existing code at `/dashboard/src/lib/optimization/tier-scoring.ts`.

**Bug 1 ($0 impact)**: The `estimateImpact()` function (lines 325-348) computes CVR deltas between current and target tier distributions, then floors at zero via `Math.max(0, ...)`. For downward movements (e.g., HIGH to MEDIUM), the target tier has lower CVR, producing negative deltas that get floored to $0. For upward movements with overlapping distributions (common with gut-assigned tiers), deltas are near-zero. The function should use ROAS-based impact estimation (aligning with the scoring engine's 50% ROAS weighting) rather than CVR-only deltas.

**Bug 2 (95% misplaced)**: The `isMisplaced` flag (line 228) fires whenever `recommendedTier !== currentTier` with zero minimum delta. With gut-assigned tiers, most terms naturally show some data-intuition disagreement. The fix requires a minimum fit score delta threshold and minimum confidence floor before flagging a term.

**UX reframing**: The word "misplaced" implies error. Since tiers were gut-assigned by the business owner, the UX should distinguish between "data-confident disagreements worth acting on" and "statistical noise".

**Primary recommendation:** Fix estimateImpact() to use ROAS-based delta estimation, add fit-score-delta and confidence thresholds to isMisplaced logic, and reframe UX language from "misplaced" to "opportunity" framing.

### Pattern 1: Calibration Configuration Object

**What:** Extract all calibration thresholds into a single config object instead of scattered constants.
**When to use:** Whenever multiple thresholds interact to produce a calibrated result.
**Example:**
```typescript
// In tier-scoring.types.ts
export interface CalibrationConfig {
  /** Minimum fit score delta between current and recommended tier to flag as opportunity */
  minFitScoreDelta: number       // Recommended: 0.3
  /** Minimum confidence score to flag a term */
  minConfidence: number          // Recommended: 0.40
  /** Minimum monthly impressions for a term to be scoreable */
  minImpressions: number         // Recommended: 50
  /** AOV for impact estimation */
  averageOrderValue: number      // Default: 85
}

export const DEFAULT_CALIBRATION: CalibrationConfig = {
  minFitScoreDelta: 0.3,
  minConfidence: 0.40,
  minImpressions: 50,
  averageOrderValue: 85,
}
```

### Pattern 2: ROAS-Based Impact Estimation

**What:** Replace CVR-only impact formula with ROAS-based estimation aligned with the scoring engine's 50% ROAS weighting.
**When to use:** When the primary scoring metric is ROAS (as it is here).
**Example:**
```typescript
export function estimateImpact(
  term: ExistingFunnelTerm,
  currentDist: TierDistribution,
  targetDist: TierDistribution,
  config: CalibrationConfig = DEFAULT_CALIBRATION
): ImpactRange {
  const monthlySpend = term.total_cost_micros / 1_000_000

  // Use ROAS delta as primary signal (aligned with 50% weighting in scoring)
  const currentRoas = currentDist.metrics.roas.p50
  const targetRoasP25 = targetDist.metrics.roas.p25
  const targetRoasP50 = targetDist.metrics.roas.p50
  const targetRoasP75 = targetDist.metrics.roas.p75

  // Impact = spend * (targetROAS - currentROAS) gives incremental revenue
  // Only positive when moving to a tier with genuinely higher ROAS
  const lowDelta = targetRoasP25 - currentRoas
  const midDelta = targetRoasP50 - currentRoas
  const highDelta = targetRoasP75 - currentRoas

  return {
    low: Math.max(0, monthlySpend * lowDelta),
    mid: Math.max(0, monthlySpend * midDelta),
    high: Math.max(0, monthlySpend * highDelta),
    currency: 'USD',
    period: 'monthly',
  }
}
```

**Why this works:** Moving a term from MEDIUM (ROAS 3.0) to HIGH (ROAS 5.5) with $50/mo spend gives $50 * (5.5 - 3.0) = $125/mo incremental revenue. This is meaningful and non-zero. The current CVR approach often yields $0 because CVR distributions overlap heavily across tiers.

### Pattern 3: Filtered isMisplaced with Delta Threshold

**What:** Add minimum fit score delta and confidence floor before flagging.
**When to use:** When raw scoring produces too many low-signal flags.
**Example:**
```typescript
// In scoreTerm():
const fitDelta = tierFitScores[recommendedTier] - tierFitScores[currentTier]
const isMisplaced = recommendedTier !== currentTier
  && fitDelta >= config.minFitScoreDelta   // Must be materially better fit
  && confidence.score >= config.minConfidence // Must have enough data to be confident

// Optional: also skip very low traffic terms
const hasEnoughData = term.total_impressions >= config.minImpressions
const isActionable = isMisplaced && hasEnoughData
```

### Anti-Patterns to Avoid
- **Removing Math.max(0, ...) from impact**: Negative impact values confuse the UX. Keep the floor but fix the formula so positive values are produced for genuine opportunities.
- **Making fit score delta too aggressive**: A delta of 1.0+ would filter out almost everything. Start at 0.3 and validate against real data.
- **Hard-coding thresholds without a config object**: Future tuning requires changing multiple scattered constants. Centralize in CalibrationConfig.
- **Changing UX and logic in the same commit**: Separate the logic fix (estimateImpact, isMisplaced) from the UX reframing (component text changes) for clean rollback.

## Common Pitfalls

### Pitfall 1: Threshold Values That Look Good on Fixtures But Fail on Production Data
**What goes wrong:** Calibration thresholds tuned to test fixtures produce different misplaced rates on real data.
**Why it happens:** Test fixtures have clean, well-separated distributions. Real gut-assigned tier data has heavy overlap.
**How to avoid:** After implementing threshold changes, test against real API response by calling the tier-scoring endpoint and examining misplaced rate. Target 10-25%. Adjust if outside range.
**Warning signs:** Misplaced rate jumps to 0% (thresholds too aggressive) or stays at 80%+ (thresholds too lenient).

### Pitfall 2: ROAS-Based Impact Producing Unrealistically Large Numbers
**What goes wrong:** For high-spend terms, ROAS deltas multiplied by spend produce impact values in the thousands per term.
**Why it happens:** ROAS deltas can be large (e.g., 5.5 - 1.0 = 4.5x) and monthly spend can be $50-100+.
**How to avoid:** Consider capping per-term impact at a reasonable maximum (e.g., $500/mo per term). Alternatively, use the low end of the impact range in hero callouts to stay conservative.
**Warning signs:** Hero callout showing "$50K/mo opportunity" for a small catalog.

### Pitfall 3: Confusing "Low Impact" with "Correctly Placed"
**What goes wrong:** A term may genuinely be in the wrong tier but have low traffic, producing $0-2 impact. The calibration might filter it out.
**Why it happens:** Minimum impression threshold + impact floor removes low-traffic terms from consideration.
**How to avoid:** This is actually desired behavior. Low-traffic misplacements aren't actionable. Document this design choice.
**Warning signs:** None -- this is working as intended.

### Pitfall 4: Downward Movement Impact Always $0
**What goes wrong:** Even with ROAS-based impact, recommending a move from HIGH to LOW produces $0 because LOW has lower ROAS.
**Why it happens:** `Math.max(0, ...)` floors negative deltas. A term in HIGH performing like a LOW term doesn't gain revenue from the move -- it saves wasted premium positioning.
**How to avoid:** For downward movements, estimate "wasted premium spend" instead of "incremental revenue." This could be computed as: `spend * (1 - targetROAS/currentROAS)` representing the spend premium being wasted. However, this is more complex and could be deferred to Phase 34 (LEAK-03 wasted spend alerts).
**Warning signs:** All downward recommendations showing $0. Consider adding a `wastedSpend` field to ImpactRange if this matters.

### Pitfall 5: MAD=0 Producing Z-Score=0 Flattens All Tiers
**What goes wrong:** When all terms in a tier have identical metrics (MAD=0), `robustZScore` returns 0 for every term, making all tiers equally good fit (score=0).
**Why it happens:** Current code returns 0 when MAD=0 (line 496). This means a term can't be distinguished between tiers when any tier has MAD=0.
**How to avoid:** Already handled gracefully in Phase 33 (returns 0, which means "no signal"). No change needed. Just document that MAD=0 tiers effectively abstain from scoring.
**Warning signs:** Groups where all tiers show 0 fit score for every term.

## Open Questions

1. **Downward movement impact representation**
   - What we know: Moving from HIGH to LOW saves wasted premium positioning but doesn't generate incremental revenue.
   - What's unclear: Should downward movements show a "wasted spend" estimate, or is $0 impact acceptable since Phase 34 (LEAK-03) handles wasted spend alerts?
   - Recommendation: For Phase 33.1, keep downward movements at $0 impact. Add a `direction` field to ImpactRange ('upward' | 'downward') so Phase 34 can compute wasted spend later.

2. **Optimal threshold values**
   - What we know: minFitScoreDelta=0.3 and minConfidence=0.40 are reasonable starting points based on code analysis.
   - What's unclear: Exact production misplaced rate with these thresholds. Real data may require adjustment.
   - Recommendation: Implement with defaults, then run against production API and adjust if rate is outside 10-25% target.

3. **Should "confirmed" terms be highlighted?**
   - What we know: Terms where data agrees with gut assignment are currently just "not flagged."
   - What's unclear: Whether Robert wants to see "data confirms your intuition" signals.
   - Recommendation: Add a `dataConfirmed` boolean to TermScore. UI can optionally show "Data-confirmed" badge. Defer prominent display to Phase 33.2 UI redesign.
