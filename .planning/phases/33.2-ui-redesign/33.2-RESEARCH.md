# Phase 33.2: Tier Intelligence UI Redesign - Research

**Researched:** 2026-02-25
**Domain:** Next.js dashboard UI redesign — action-oriented data presentation
**Confidence:** HIGH

## Summary

Phase 33.2 transforms the Tier Intelligence page from a 4-level statistical drill-down (Groups > Group > Tier > Term) into an action-oriented decision-making interface. The current page shows all ~4,000 terms across 59 product groups with z-scores, MAD, p25/p50/p75 — useful for data scientists but meaningless to the business owner (Robert) and operator (Bobby).

The redesign preserves the existing scoring engine (`tier-scoring.ts`) and API route (`/api/shopping-funnel/tier-scoring`) untouched. All changes are presentation-layer only: replacing the 4-level navigation with a priority action queue, translating statistical verdicts to plain English, and hiding statistical details behind progressive disclosure. The existing component files (10 `.tsx` files in `tier-scoring/components/`) will be restructured.

**Primary recommendation:** Replace the current `page.tsx` with a two-panel layout: (1) hero summary card with dollar opportunity, (2) prioritized top-N action queue of misplaced terms sorted by impact. Preserve GroupOverview/GroupDetail/TierDetail/TermScorecard behind a "Show all groups" toggle or tab for operator deep-dives.

### Pattern 1: Two-View Tabs
**What:** Use shadcn/ui Tabs at the top of the page to switch between "Action Queue" (default) and "Explorer" views.
**When to use:** When users have two distinct workflows (Robert's 2-min scan vs Bobby's 10-min deep dive).
**Example:**
```typescript

      <PageHeader computedAt={data?.computedAt} onRefresh={refresh} />
      <Tabs defaultValue="actions">
        <TabsList>
          <TabsTrigger value="actions">Action Queue</TabsTrigger>
          <TabsTrigger value="explorer">Explorer</TabsTrigger>
        </TabsList>

        </TabsContent>
        <TabsContent value="explorer">
          <ExplorerView data={data} />
        </TabsContent>
      </Tabs>
    </div>

```

### Pattern 2: Plain English Verdict Generator
**What:** Transform TermScore fields into business-friendly sentences at the component level (not API level). The API already generates a `verdict` string, but it still references "fit" and tier names without context.
**When to use:** Every place a term is displayed in the Action Queue view.
**Example:**
```typescript
function generatePlainVerdict(term: TermScore): string {
  const roasStr = (term.tierFitScores[term.currentTier] !== undefined)
    ? `earning ${getTermRoas(term).toFixed(1)}x return`
    : ''

  if (!term.isMisplaced) {
    return term.dataConfirmed
      ? `This term is performing well in ${term.currentTier} — data confirms the placement`
      : `This term appears correctly placed in ${term.currentTier}`
  }

  const direction = tierRank[term.recommendedTier] > tierRank[term.currentTier]
    ? 'could handle higher-value placement'
    : 'may be overpaying for its current tier'

  const impactStr = term.impact
    ? ` — potential ${formatDollars(term.impact.low)}-${formatDollars(term.impact.high)}/mo improvement`
    : ''

  return `This term is ${roasStr} but ${direction}${impactStr}`
}
```

### Pattern 3: Top-N Prioritized Action Queue
**What:** Filter misplaced terms from API response, sort by `impact.mid` descending, take top 15-20.
**When to use:** Default view — replaces GroupOverview as the landing experience.
**Example:**
```typescript
const actionQueue = useMemo(() => {
  if (!data?.scores) return []
  return data.scores
    .filter(s => s.isMisplaced)
    .sort((a, b) => (b.impact?.mid ?? 0) - (a.impact?.mid ?? 0))
    .slice(0, 20) // Top 20 highest-impact terms
}, [data?.scores])
```

### Pattern 4: Progressive Disclosure with Collapsible
**What:** Statistical details (z-scores, distributions, MAD, confidence factors) are hidden by default and revealed on demand.
**When to use:** When an operator clicks "Show details" on an action queue row, or navigates to Explorer view.
**Example:** Already implemented in TermScorecard via `Collapsible` component. Extend this pattern to action queue rows.

### Anti-Patterns to Avoid
- **Don't remove the 4-level drill-down:** It has value for operator deep-dives. Hide it behind the Explorer tab, don't delete it.
- **Don't change the API response shape:** The `TierScoringResponse` interface works. All transformation happens client-side.
- **Don't change the scoring engine:** `tier-scoring.ts` is tested and calibrated. Zero changes needed.
- **Don't add new API endpoints:** The existing `/api/shopping-funnel/tier-scoring` returns all needed data.
- **Don't over-engineer the verdict generator:** Keep it as a pure function that reads TermScore fields. No new state, no API calls.

## Common Pitfalls

### Pitfall 1: Removing Statistical Details Instead of Hiding Them
**What goes wrong:** Deleting the TermScorecard, DistributionChart, and confidence breakdown removes operator value.
**Why it happens:** The phase goal says "plain English" which tempts developers to gut the statistical views entirely.
**How to avoid:** Use two-view architecture (Tabs). Action Queue = plain English. Explorer = full statistics. Both share the same data.
**Warning signs:** If a plan task says "remove" TermScorecard or DistributionChart.

### Pitfall 2: Trying to Change the API or Scoring Engine
**What goes wrong:** Modifying `tier-scoring.ts` or the API route to pre-compute plain English verdicts or pre-filter top-N. This creates regression risk in calibrated scoring.
**Why it happens:** Seems cleaner to do server-side, but introduces unnecessary coupling.
**How to avoid:** All transformation (plain English, top-N filtering, sorting) happens in the page/component layer. The API returns the full dataset as it does today.
**Warning signs:** Any changes to files outside `dashboard/src/app/(dashboard)/tier-scoring/`.

### Pitfall 3: Duplicating State Management
**What goes wrong:** The current page manages 4 state variables (selectedGroup, selectedTier, selectedTerm, data). Adding a second view doubles the state complexity.
**How to avoid:** Extract data fetching into `useTierScoring()` hook. Each view manages its own navigation state independently. The hook provides the shared data.
**Warning signs:** More than 6-7 useState calls in page.tsx.

### Pitfall 4: Breaking Mobile Layout
**What goes wrong:** Action queue rows with term name, tier arrows, impact range, confidence badge, and verdict can overflow on mobile.
**Why it happens:** Current MisplacedTermRow uses horizontal flex layout that breaks at narrow widths.
**How to avoid:** Use responsive stacking: show full row on desktop (`lg:`), stack verdict below on mobile. Test at 375px width.
**Warning signs:** `hidden lg:block` on critical information.

### Pitfall 5: Import Cleanup Breaking Other Files
**What goes wrong:** Moving components to `views/` or `shared/` subdirectories changes import paths. The page currently uses relative imports (`./components/HeroCallout`).
**Why it happens:** Refactoring component organization.
**How to avoid:** Either keep components flat in `components/` and add new files there, or update ALL imports when restructuring. Run `npm run build` after every file move.
**Warning signs:** TypeScript errors about missing modules after reorganization.

### Pitfall 6: CTA Buttons That Do Nothing
**What goes wrong:** Adding "Apply Recommendations" or "Move to HIGH" buttons that have no handler because Phase 34 hasn't been built yet.
**Why it happens:** CONTEXT.md describes Phase 34 CTAs as part of the target experience.
**How to avoid:** Use disabled buttons with tooltips: "Coming soon — Phase 34 will enable one-click tier movements". This preserves the visual intent without dead clicks.
**Warning signs:** onClick handlers that are empty functions or `console.log`.

### Shared formatDollars Utility (Extracted)
```typescript
// dashboard/src/lib/formatting.ts
export function formatDollars(amount: number): string {
  if (Math.abs(amount) >= 1000) {
    return `$${(amount / 1000).toFixed(1)}K`
  }
  return `$${amount.toLocaleString('en-US', { maximumFractionDigits: 0 })}`
}
```

### useTierScoring Hook (Extracted)
```typescript
// hooks/useTierScoring.ts
export function useTierScoring() {
  const [data, setData] = useState<TierScoringResponse | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<string | null>(null)

  const fetchScores = useCallback(async (forceRefresh = false) => {
    setLoading(true)
    setError(null)
    try {
      const url = forceRefresh
        ? '/api/shopping-funnel/tier-scoring?forceRefresh=true'
        : '/api/shopping-funnel/tier-scoring'
      const res = await fetch(url)
      if (!res.ok) {
        const body = await res.json().catch(() => ({}))
        throw new Error(body.error || `API returned ${res.status}`)
      }
      setData(await res.json())
    } catch (err) {
      setError(err instanceof Error ? err.message : 'Failed to load')
    } finally {
      setLoading(false)
    }
  }, [])

  useEffect(() => { fetchScores() }, [fetchScores])

  return { data, loading, error, refresh: fetchScores }
}
```
