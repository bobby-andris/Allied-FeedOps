# Phase 25.4: Production Impact Audit - Research

**Researched:** 2026-02-24
**Domain:** Python pipeline source code regression analysis (v1 production path safety)
**Confidence:** HIGH

## Summary

The v1.3a branch (`v1.3a/prompt-rewrite-validation`) has only 3 documentation-only commits ahead of master. **All 24+ source code changes from Phases 23-25.3 were committed directly to master**, meaning they are already deployed to production Cloud Run. The audit scope is therefore NOT "will merging break production" but rather "what has already changed in the v1 production path, and are there regressions?"

The feature flag `FEEDOPS_PROMPT_VERSION` defaults to `"v1"` and correctly gates all v2-specific code paths in `main.py`, `generator.py`, and `hybrid_generation.py`. However, several changes to shared modules affect the v1 path directly. The most significant finding is **three behavioral changes that affect all API calls regardless of feature flag**: (1) reasoning_effort now defaults to `"high"` instead of being absent, (2) max_completion_tokens increased from 2000 to 8000, and (3) response format changed from `json_object` to strict `json_schema`. Additionally, the CANDIDATE_SCHEMA self_score fields were renamed (breaking `parse_candidate_response()` which still reads old field names), and SYSTEM_PROMPT was completely rewritten.

**Primary recommendation:** These changes are already deployed. The audit should classify each change as intentional-improvement vs unintentional-regression, verify the v1 path still produces valid content with the new parameters, and document any rollback-worthy issues.

## Critical Findings

### Finding 1: CANDIDATE_SCHEMA self_score Mismatch (HIGH -- REGRESSION)
**What:** CANDIDATE_SCHEMA self_score fields changed from `{specificity, benefit_coverage, keyword_inclusion, format_adherence, brand_voice, factual_accuracy}` to `{hook_quality, product_specificity, competitive_diff, keyword_integration, customer_scenario, emotional_resonance, factual_accuracy, platform_compliance, finish_integration, variety_score}`.

**Impact on v1:** `parse_candidate_response()` in generator.py reads old field names with `.get("specificity", 5)` etc. Since the LLM now returns new field names (because CANDIDATE_SCHEMA is the strict schema), all old-name fields get default value 5. Score is always 50% composite. The `factual_accuracy` field name is shared between old and new schemas, so that one field works correctly.

**v1 path affected:** `build_split_prompt()` -> `generate_candidates()` -> `parse_candidate_response()` -- this is the v1 path inside `generate_per_platform()` when prompt_version="v1".

**Actual severity:** MEDIUM-LOW in practice because:
- Production currently runs v1 (`FEEDOPS_PROMPT_VERSION` unset = "v1")
- The v1 path in optimize_sku/regenerate uses `build_core_prompt()` with simple `{"content": "string"}` schema, NOT CANDIDATE_SCHEMA
- CANDIDATE_SCHEMA is only used by `generate_candidates()` / `build_split_prompt()` which is the generator.py v1 fallback path
- The main.py v1 path does NOT call `generate_per_platform()` -- it calls `build_core_prompt()` directly
- But batch_optimize and hybrid-generate v1 paths DO use `build_core_prompt()`, not `generate_candidates()`

**Conclusion:** The CANDIDATE_SCHEMA + parse_candidate_response mismatch exists but is NOT exercised by the production v1 code path in main.py. It would only be triggered if someone called `generate_candidates()` directly (e.g., from optimize.py or test code).

### Finding 2: OpenAI Provider Behavioral Changes (HIGH -- INTENTIONAL)
**What:** Three simultaneous changes to how ALL LLM calls work:
1. `reasoning_effort` defaults to `"high"` (was absent when env var unset)
2. `response_format` uses strict `json_schema` (was `json_object`)
3. `temperature=0.7` dropped when `reasoning_effort` is set (mutual exclusion)
4. `max_completion_tokens` default 2000 -> 8000

**Impact:** These were intentional bug fixes (Phase 23, commit a7a285d8) addressing documented GPT-5.2 issues. They affect ALL API calls regardless of feature flag. The changes are already deployed and presumably working in production since the Cloud Run service is operational.

**Risk assessment:** These changes improve behavior (reasoning was broken before, temperature conflicted with reasoning, json_schema is more reliable). The 4x token budget increase means higher cost per call but prevents truncation. Already deployed and presumably validated by Phase 25.3 testing.

### Finding 3: SYSTEM_PROMPT Rewrite (MEDIUM -- INTENTIONAL)
**What:** The SYSTEM_PROMPT constant was completely rewritten from a traditional prompt to an XML-tagged creative brief with explicit brand voice rules, accuracy guardrails, and scoring rubric.

**Impact on v1:** `get_system_prompt()` returns `SYSTEM_PROMPT + skills`. The v1 path uses this directly. Content generated via v1 path uses the new system prompt. This is an intentional quality improvement that affects v1 output.

## Common Pitfalls

### Pitfall 1: Assuming Branch Merge is the Risk Point
**What goes wrong:** Phase 25.4 was created to audit "before merging to master" -- but the source changes are already on master.
**Why it happens:** The branch was created AFTER the source changes were committed to master, as a documentation/planning branch.
**How to avoid:** Run `git diff master...HEAD -- src/` first to confirm what actual source changes exist on the branch.

### Pitfall 2: CANDIDATE_SCHEMA / Score Model Drift
**What goes wrong:** Schema field names changed but the Pydantic model and parser were not updated together.
**Why it happens:** CANDIDATE_SCHEMA was updated as part of the quality rubric redesign (Phase 23, commit 751b549f) but `Score` model in `models/score.py` and `parse_candidate_response()` in `generator.py` were not updated.
**How to avoid:** The schema, model, and parser should be updated atomically. Any schema change needs a grep for all consumers.
**Warning signs:** Tests that construct Score objects will fail; parse_candidate_response will silently return default scores.

### Pitfall 3: "Safe" Parameter Changes in Shared Providers
**What goes wrong:** Changing defaults in openai_provider.py (reasoning_effort, max_tokens, response_format) affects every code path.
**Why it happens:** The provider is a shared layer beneath all v1 and v2 code.
**How to avoid:** Parameter changes in the provider should be treated as global changes. Test both v1 and v2 paths after any provider change.
