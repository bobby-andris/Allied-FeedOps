# Phase 34.1 — Fix Decision Logic

## Status: Ready to Plan

## The Problem (verified via production browser inspection)

The Tier Intelligence dashboard produces **backwards recommendations**. Out of 155 flagged terms:
- 154 show $0 impact
- Almost all recommend moving from HIGH → LOW
- Terms with 0.0 ROAS are recommended for LOW (aggressive bidding) — the worst possible advice

## Five Interconnected Bugs

### Bug 1: recommendedTier picks "best fit" not "best action"
**File**: `dashboard/src/lib/optimization/tier-scoring.ts` lines 228-231
**Problem**: `recommendedTier` = tier whose observed distribution the term's metrics are closest to (smallest absolute z-score). For 0.0 ROAS terms, LOW's observed distribution (p50=0.3x) is closest, so the engine says "move to LOW."
**Root cause**: The engine is DESCRIPTIVE (you look like other LOW terms) not PRESCRIPTIVE (moving you to LOW would unleash aggressive bidding on a non-converter).
**Fix direction**: For wasted spend terms, override recommendedTier based on business logic, not fit scores. Wasted spend should go to HIGH (constrain) or be blocked — never to LOW.

### Bug 2: Wasted spend direction not overridden
**File**: `dashboard/src/app/(dashboard)/tier-scoring/lib/reason-codes.ts` lines 40-42
**Problem**: `classifyLeakageReason()` correctly tags terms as `wasted_spend` but doesn't override the `recommendedTier` from `scoreTerm()`. So you get "Wasted $ — recommend HIGH → LOW."
**Fix direction**: When reasonCode = wasted_spend, force recommendedTier to 'HIGH' (if not already) or mark as 'block' candidate.

### Bug 3: "Constrain" button for wasted spend already in HIGH is a no-op
**File**: `dashboard/src/app/(dashboard)/tier-scoring/components/LeakageTermRow.tsx` lines 82-87
**Problem**: `handleDemote` sends `recommendedTier: 'high'`. If `currentTier === 'HIGH'`, this does nothing. Only valid action for wasted-spend-in-HIGH is Block or Accept.
**Fix direction**: Check currentTier before showing Constrain. If already HIGH, show only Block/Accept.

### Bug 4: Impact formula returns $0 for 154/155 terms
**File**: `dashboard/src/lib/optimization/tier-scoring.ts` lines 355-392
**Problem**: `estimateImpact()` computes `targetRoasP25 - currentRoas`. For HIGH→LOW: current=HIGH p50 (1.6x), target=LOW p25 (~0x). Delta is negative, `Math.max(0, ...)` = $0.
**Root cause**: LOW's observed distributions reflect a broken funnel (full of zero-ROAS terms), so moving TO LOW looks like a downgrade.
**Fix direction**: Impact should use the TERM's actual ROAS vs. the target tier's expected ROAS, not the tier distributions against each other. Or: for wasted spend, impact = cost saved by constraining/blocking.

### Bug 5: Verdict text is descriptive, not prescriptive
**File**: `dashboard/src/lib/optimization/tier-scoring.ts` lines 257-258
**Problem**: "This term is a strong fit for LOW because its ROAS (0.0) aligns with LOW tier distributions" — technically true (0.0 fits LOW's junk data) but misleading.
**Fix direction**: Verdicts for wasted spend should say "This term has spent $X with zero conversions — recommend blocking or constraining in HIGH."

## Observed Distributions (from production dashboard)

- Premium (HIGH): 1.6x ROAS median
- Mid-tier (MEDIUM): 1.9x ROAS median
- Budget (LOW): 0.3x ROAS median

These are from REAL data. LOW is full of zero-converting terms — a broken funnel that the scoring engine treats as ground truth.

## DEFAULT_DISTRIBUTIONS (from code, used when no data)

- HIGH: p50=1.2x (idealized broad/constrained)
- MEDIUM: p50=3.0x (idealized mid-funnel)
- LOW: p50=5.5x (idealized high-intent/aggressive)

The defaults represent the IDEAL waterfall. The real data shows the funnel is broken.

## Additional Requirements from User (2026-02-26)

### 6. Custom Label 0 Level Blocking
User wants ability to block an ENTIRE custom_label_0 (product category) across all funnels. Example: if "baskets" consistently wastes money, block ALL search terms under that custom_label_0 at once. This is a category-level action, not per-term.

### 7. Shopping → Search Campaign Pipeline (Search Promoter)
**Strategic insight**: Shopping campaigns exist primarily to DISCOVER which keywords generate actual revenue. High-performing keywords found via Shopping are then "promoted" to Search campaigns with the SAME waterfall tier structure.

The dashboard should surface: "These Shopping terms are proven converters — promote them to Search campaigns."

This is the bigger picture: Shopping = keyword discovery engine → Search = revenue scaling engine.

### 8. Cross-Category & Pattern-Level Insights
- Which custom_label_0 groups are profitable vs unprofitable overall?
- Cross-term patterns (all "grab bar" terms converting well → systemic promotion)
- Finish-level analysis (do "polished nickel" terms convert differently than "oil rubbed bronze"?)
- Which terms should be promoted from Shopping to Search?
