**Create `tests/test_jobs/test_processor.py`:**

Mock the job manager functions (`create_job`, `get_job`, `update_job_status`, etc.) and provide mock `process_fn` callables.

Tests:

1. `test_processes_all_items_in_batches` (async): Create processor with 25 items, batch_size=10. Mock process_fn that records calls. Run. Assert process_fn called 3 times (batches of 10, 10, 5). Assert job status set to 'complete'.

2. `test_checkpoint_resume` (async): Create processor with 50 items. Mock `get_job` to return checkpoint_data={"batch_index": 20}. Run. Assert process_fn only receives items from index 20 onward (30 items in 3 batches).

3. `test_checkpoint_saved_at_interval` (async): Create processor with 250 items, checkpoint_interval=100. Run. Assert `save_checkpoint` called at least 2 times (at items 100 and 200).

4. `test_transient_error_retried_with_backoff` (async): Create processor with 10 items. Mock process_fn to raise a rate limit error on first call, succeed on second. Assert process_fn called 2 times for that batch. Assert job completes successfully.

5. `test_permanent_error_logged_and_continues` (async): Create processor with 20 items (2 batches). Mock process_fn to raise ValueError on first batch, succeed on second. Assert `log_job_error` called once. Assert second batch still processed. Assert job status is 'complete' (1 batch failed out of 2, but >95% items succeeded since batch 2 had 10 items).

6. `test_concurrent_job_limit` (async): Mock `get_active_job_count` to return 3. Call start_backfill. Assert HTTPException(429) raised.

7. `test_progress_updates_every_batch` (async): Create processor with 30 items, batch_size=10. Run. Assert `update_job_progress` called 3 times.

8. `test_partial_status_when_low_success_rate` (async): Create processor with 100 items, batch_size=10. Mock process_fn to fail on 6 out of 10 batches (60 items failed). Assert job status is 'partial' (only 40% success).

9. `test_idempotent_upsert_contract` (async): Validates JOB-06 — process_fn implementations MUST use idempotent upserts. Create a mock process_fn that simulates a Supabase `.upsert()` call with `on_conflict` parameter. Create processor with 10 items (e.g., ["SKU-1", ..., "SKU-10"]), batch_size=5. Run the processor TWICE with the same items (simulating a retry/resume scenario). The mock process_fn should track all upsert calls and their `on_conflict` args. Assert: (a) process_fn used `.upsert()` not `.insert()` — verify via mock call inspection, (b) running the same items twice does NOT produce duplicate records — the mock should maintain a dict keyed by item_id, and after two runs the dict has exactly 10 entries (not 20), (c) the `on_conflict` parameter was specified in every upsert call. This test proves the upsert pattern works and documents the contract for Phase 2 implementors.

Use `pytest.mark.asyncio` for async tests. Use `unittest.mock.AsyncMock` for async mock functions.

For mocking the manager imports inside processor.run(), use `@patch("feedops.jobs.processor.update_job_progress")` style patching since processor imports manager functions inside run().

Actually, since processor imports manager functions at call time (inside run()), mock them via `@patch("feedops.jobs.manager.get_job")` etc. — use the canonical import path.
