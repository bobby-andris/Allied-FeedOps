```python
class TokenBucket:
    """Thread-safe token bucket rate limiter.

    Allows burst up to capacity, refills at constant rate.
    Thread-safe for use across multiple async tasks in same process.
    """

    def __init__(self, rate: float, capacity: int):
        """
        Args:
            rate: Tokens added per second (e.g., 10.0 for 10 QPS)
            capacity: Maximum tokens (burst capacity)
        """
```

Methods:
- `consume(tokens: int = 1) -> bool`: Synchronous. Try to consume tokens, return True if allowed. Uses `threading.Lock` for thread safety. Refills tokens based on elapsed time since last refill using `time.monotonic()`.
- `async acquire(tokens: int = 1) -> None`: Async. Wait until tokens available. Poll every 10ms using `asyncio.sleep(0.01)`. Log a warning if waiting exceeds 5 seconds (indicates sustained rate limiting).
- `available_tokens -> float`: Property returning current token count (after refill calculation).

**Pre-configured instances (module-level):**
- `google_ads_limiter = TokenBucket(rate=10.0, capacity=20)` — 10 QPS with burst to 20
- `keyword_planner_limiter = TokenBucket(rate=2.0, capacity=5)` — Lower rate for Keyword Planner

Create a generic batch processor that any data collection pipeline can use.

**Class: BatchProcessor**

This is an abstract-ish base class. Subclasses (in Phase 2) will implement `process_item()` for specific data types. But BatchProcessor itself handles all the infrastructure: batching, checkpointing, error handling, progress tracking, rate limiting.

```python
class BatchProcessor:
    """Generic batch processor with checkpointing, rate limiting, and error handling.

    Usage:
        processor = BatchProcessor(
            job_id="abc-123",
            items=["SKU-1", "SKU-2", ...],
            batch_size=10,
            checkpoint_interval=100,
            rate_limiter=google_ads_limiter,
        )
        await processor.run(process_fn=my_async_function)
    """
```

Constructor args:
- `job_id: str` — The backfill_jobs UUID
- `items: list[str]` — List of item IDs (SKUs, offer IDs, etc.)
- `batch_size: int = 10` — Items per batch (DATA-06)
- `checkpoint_interval: int = 100` — Save checkpoint every N items (JOB-09)
- `rate_limiter: TokenBucket | None = None` — Optional rate limiter
- `max_retries: int = 3` — Max retries per item on transient errors

**Method: `async run(process_fn: Callable[[list[str]], Awaitable[list[dict]]])`**

The `process_fn` receives a batch of item IDs and returns a list of result dicts. It is called once per batch.

Implementation flow:
1. Import `get_job`, `update_job_status`, `update_job_progress`, `save_checkpoint`, `log_job_error` from `feedops.jobs.manager` (import inside method to avoid circular imports — manager.py doesn't exist yet when this module loads during Wave 1 parallel execution, but will exist by Wave 2 when this code runs).
2. Load job from DB to get checkpoint_data
3. Resume from `checkpoint_data["batch_index"]` if exists, else start from 0
4. Set job status to 'running'
5. Record start time (`time.time()`)
6. Loop through items in batches:
   a. If rate_limiter, call `await rate_limiter.acquire()`
   b. Try calling `process_fn(batch)` with retry logic:
      - On rate limit / transient error (check using `is_retryable_provider_error` from `feedops.providers.reliability`): exponential backoff using `compute_backoff_seconds`, retry up to max_retries
      - On permanent error: log error via `log_job_error`, continue to next batch
   c. Increment completed count
   d. Update progress via `update_job_progress` every batch
   e. Every `checkpoint_interval` items, call `save_checkpoint` with `{"batch_index": current_index, "last_item": last_item_in_batch}`
7. After loop, determine final status:
   - If failed_items == 0: status = 'complete'
   - If failed_items > 0 and completed_items / total_items >= 0.95: status = 'complete' (some failures acceptable)
   - If completed_items / total_items < 0.95: status = 'partial'
8. Update job status with completed_at timestamp

**CRITICAL implementation notes:**
- Import from `feedops.jobs.manager` INSIDE the `run()` method, NOT at module top level. This avoids import ordering issues since 05-01 and 05-02 execute in parallel (Wave 1).
- Import `compute_backoff_seconds` and `is_retryable_provider_error` from `feedops.providers.reliability` at module level (this module already exists).
- Use `asyncio.sleep()` for backoff waits (not `time.sleep()` since this runs in async context).
- All data writes done by `process_fn` MUST use idempotent upserts (ON CONFLICT). Document this in the docstring as a contract for process_fn implementors (JOB-06).
- Log progress with `logger.info()` every batch: "Job {job_id}: processed {completed}/{total} items ({pct}%)"
