**In `prompt_builder.py`**, add 4 new functions alongside existing `build_user_prompt()` (do NOT remove existing function — used by old codepath):

1. **`build_google_prompt(sku_data, evidence, keywords, category_guidance, gold_examples) -> str`**
   - Assembles user prompt for Google generation
   - Includes: product evidence table, keyword data, category-specific guidance, gold standard examples for Google titles/descriptions
   - Explicitly defines `{FINISH_NAME}` as a placeholder: "This content is for a variant-level Google Shopping listing. Use the literal string {FINISH_NAME} where the finish name belongs. Use the literal string {FINISH_SENTENCE} where finish context flows naturally. These are placeholders that will be replaced during variant publishing."
   - Does NOT include Bing or Shopify rules

2. **`build_bing_prompt(sku_data, evidence, keywords, category_guidance) -> str`**
   - Similar to Google but instructs: front-load specifications in first 200 chars, broader synonym coverage, Bing-specific optimization
   - Same {FINISH_NAME} and {FINISH_SENTENCE} placeholder instructions

3. **`build_shopify_prompt(sku_data, evidence, category_guidance) -> str`**
   - Assembles user prompt for Shopify master-SKU content
   - Explicitly states: "This is master-SKU content — do NOT mention any specific finish. The content must work for all 28 finish variants."
   - Instructs HTML format, buyer-problem-first opening, trust signals
   - Does NOT include {FINISH_NAME} or {FINISH_SENTENCE} references

4. **`build_finish_prompt(sku_data, finish_metadata) -> str`**
   - Assembles prompt for generating 28 product-specific finish sentences
   - Includes: product type, collection, key product features, and the full finish metadata (28 finishes with visual descriptions from `get_finish_metadata()`)
   - Instructs: "Each sentence must be specific to THIS product paired with THIS finish. Not generic — a Waverly Place towel bar in Satin Brass needs a different sentence than a Continental soap dish in Matte Black."

All functions reuse existing evidence building from `prompt_builder.py` (`build_evidence_table()`, `format_evidence_markdown()`) — do not rebuild these.

**In `generator.py`**, add `generate_per_platform()` function:

```python
async def generate_per_platform(
    parent_sku: ParentSKU,
    provider: OpenAIProvider,
    prompt_version: str = "v2",  # "v1" = old single call, "v2" = per-platform
) -> dict:
```

This function:
1. If `prompt_version == "v1"`, delegates to existing `generate_content()` (backward compat)
2. If `prompt_version == "v2"`:
   - Loads product data via existing `prompt_loader.py` functions
   - Calls `build_google_prompt()` + `get_platform_system_prompt("google")` → GPT-5.2 with GOOGLE_SCHEMA
   - Calls `build_bing_prompt()` + `get_platform_system_prompt("bing")` → GPT-5.2 with BING_SCHEMA
   - Calls `build_shopify_prompt()` + `get_platform_system_prompt("shopify")` → GPT-5.2 with SHOPIFY_SCHEMA
   - Calls `build_finish_prompt()` + `get_platform_system_prompt("finish")` → GPT-5.2 with FINISH_SENTENCES_SCHEMA
   - Merges results into a single dict matching the expected `generated_content` table schema
   - All 4 calls can run concurrently (asyncio.gather) for speed — per CONTEXT.md, Claude's discretion on parallel vs sequential

3. Uses `reasoning_effort="medium"` (adjustable based on Plan 01 test results)
4. Uses `max_completion_tokens=4000` per call
5. Logs token usage per platform call for cost tracking

**Handle the `prompt_version` feature flag:**
- Read from env var `FEEDOPS_PROMPT_VERSION` (default: `"v1"` for safe rollback)
- When set to `"v2"`, uses per-platform architecture
- This allows deploying to Cloud Run and testing without breaking production

**Per CONTEXT.md locked decision:** 3 calls for ALL SKUs — quality is the priority, no cost shortcuts. But the feature flag allows safe rollback if issues arise.

**Per RESEARCH.md Pitfall 5 (regression):** Do NOT modify existing `get_system_prompt()`, `build_split_prompt()`, `build_variant_prompt()`, or `build_user_prompt()`. Add new functions alongside them. The feature flag controls which codepath is used.

**Store finish sentences — CRITICAL WIRING:**

The FINISH_SENTENCES_SCHEMA produces an array: `{"sentences": [{"finish_code": "ABR", "finish_name": "Antique Brass", "sentence": "..."}, ...]}`.

The `variant_finish_sentences` table stores `finish_sentences` as a JSONB column. The consumer (`expand-variants.ts` line 66, `normalizeFinishSentences()`) expects this JSONB value to be a `Record<string, string>` — an object keyed by finish code with sentence values: `{"ABR": "sentence text...", "PB": "sentence text...", ...}`.

**The generator MUST transform** the FINISH_SENTENCES_SCHEMA array output into the object format before upserting:
```python
# Transform array to object for DB storage
finish_map = {s["finish_code"]: s["sentence"] for s in result["sentences"]}
# Upsert to variant_finish_sentences with finish_map as finish_sentences value
```

Upsert to `variant_finish_sentences` table using: `master_sku`, `platform` (one row per platform — "google" and "bing"), `finish_sentences` (the transformed object). Use existing Supabase upsert pattern from the codebase.
