**1. `collect_search_terms_batch(batch: list[str]) -> list[dict]`** (DATA-01, DATA-10)

This worker collects search terms for a batch of master SKUs using the existing SearchTermsClient:

- Import `SearchTermsClient` from `feedops.integrations.google_ads_search_terms`
- Import `compute_date_range` from `feedops.api.backfill` for explicit YYYY-MM-DD dates (DATA-07)
- Create a SearchTermsClient instance
- Call `client.fetch_search_terms(days=180)` to get search terms using the campaign-join pattern (DATA-01: 2-step query already implemented in SearchTermsClient)
- Call `client.save_search_terms_to_db(terms, period_start, period_end, sync_job_id=None)` which already uses idempotent upserts with `ON CONFLICT (query_text, gmc_offer_id, period_start, period_end)`
- The function fetches ALL search terms in one call (campaign-join pattern is batch-native, not per-SKU). The `batch` parameter is used to filter results to only relevant SKUs after collection
- Return list of dicts with `{"item_id": sku, "status": "ok"}` for each processed SKU, or `{"item_id": sku, "status": "no_data"}` if no search terms found for that SKU

IMPORTANT: The SearchTermsClient.fetch_search_terms() uses LAST_N_DAYS syntax internally but the save_search_terms_to_db() takes explicit date params. Use `compute_date_range(180)` to generate the period_start and period_end for saving.

IMPORTANT: The campaign-join pattern fetches ALL search terms across all campaigns, not per-SKU. The batch of SKUs is used to filter which results we care about. The worker should:
1. Call fetch_search_terms(days=180) once for the batch
2. Filter results to only include terms where master_sku is in the batch
3. Save filtered results via save_search_terms_to_db()

**2. `collect_performance_batch(batch: list[str]) -> list[dict]`** (DATA-02, DATA-05, DATA-09, DATA-10)

This worker collects 180-day performance metrics for a batch of master SKUs:

- Import `fetch_batch_product_performance` from `feedops.integrations.google_ads_performance`
- Import `get_client` from `feedops.db.supabase_client`
- Use `compute_date_range(180)` for explicit date range (DATA-07)
- For each master_sku in the batch:
  1. Query `variant_index` to get all `gmc_offer_id` values for that master_sku
  2. Call `fetch_batch_product_performance(offer_ids, start_date, end_date)` to get metrics (impressions, clicks, CTR, conversions + competitive metrics like impression_share/click_share where available per DATA-09)
  3. Aggregate variant-level metrics to master_sku level (sum impressions/clicks/conversions, weighted avg CTR)
  4. Upsert to `performance_baselines` table with:
     - master_sku, platform='google'
     - avg_impressions (total_impressions / days), avg_clicks, avg_ctr, avg_conversions
     - Use `.upsert()` with `on_conflict="master_sku,platform"` for idempotency
     - Include `captured_at` timestamp (DATA-10)
     - Include `date_range_start` and `date_range_end` fields (DATA-05)
- Return list of result dicts

NOTE: The `fetch_batch_product_performance` function already handles the IN clause batching and returns `{offer_id: {impressions, clicks, ctr, conversions, conversion_value, cost, roas, daily_data}}`. Aggregate across all variants of a master_sku.

NOTE: Check `performance_baselines` schema in SCHEMA.md for exact column names before writing upsert logic. The table has `(master_sku, platform)` as the conflict target.

Add module docstring explaining the workers module purpose, the process_fn contract (idempotent upserts required), and links to Phase 1 infrastructure.

**3. `collect_keyword_planner_batch(batch: list[str]) -> list[dict]`** (DATA-03, DATA-10)

This worker generates Keyword Planner ideas for a batch of master SKUs:

- Import `KeywordPlannerClient` from `feedops.integrations.google_ads_search_terms`
- Create a KeywordPlannerClient instance
- For each master_sku in the batch:
  1. Query `variant_index` for the master_sku to get product_title (used as seed keyword)
  2. Also query `search_queries` for top existing search terms for this SKU (up to 5) to use as additional seed keywords
  3. Build keyword list: [product_title] + top search terms
  4. Call `client.get_historical_metrics(keywords, use_cache=True, cache_max_age_days=30)` (DATA-03: 30-day TTL caching is built into KeywordPlannerClient)
  5. The KeywordPlannerClient already handles saving to `keyword_metrics` table with proper caching
- Return list of result dicts with `{"item_id": sku, "status": "ok", "keywords_enriched": N}`

NOTE: KeywordPlannerClient.get_historical_metrics() already checks cache and only queries the API for keywords not cached within cache_max_age_days. This means re-running for the same SKU within 30 days is essentially free.

NOTE: The keyword_planner_limiter (2 QPS) is applied at the BatchProcessor level, not inside this worker. The BatchProcessor calls `await rate_limiter.acquire()` before each batch.

**4. `collect_custom_labels_batch(batch: list[str]) -> list[dict]`** (DATA-04, DATA-10)

This worker syncs custom_label_0 from Google Merchant Center to Supabase:

- Import `fetch_merchant_center_items` from `feedops.integrations.merchant_center`
- Import `get_client` from `feedops.db.supabase_client`
- The GMC API returns all products at once (not per-SKU), so this worker should:
  1. Call `fetch_merchant_center_items()` to get all products with customLabel0 through customLabel4 fields
  2. Build a lookup dict: `{offerId: customLabel0}` from the results
  3. For each master_sku in the batch:
     a. Query `variant_index` to get all `gmc_offer_id` values for that master_sku
     b. Look up customLabel0 from the GMC data by offer_id
     c. Upsert to `variant_index` with the custom_label_0 value
     d. Use `.update().eq("gmc_offer_id", offer_id)` since variant_index has unique gmc_offer_id
  4. Include `updated_at` timestamp in the update (DATA-10)
- Return list of result dicts

NOTE: The variant_index table may not have a `custom_label_0` column yet. Check SCHEMA.md. If it doesn't exist, the worker should store custom labels in the `product_catalog` table instead (which has a `custom_labels` JSONB column) or log a warning. Check the actual schema and use the appropriate table.

IMPORTANT: The GMC API call is expensive (fetches ALL products). For efficiency, call it ONCE at the start of the batch and reuse the result dict for all SKUs in the batch. Consider caching the GMC data in a module-level variable with a TTL to avoid re-fetching for every batch.

Also update `src/feedops/jobs/__init__.py` to export all 4 worker functions.
