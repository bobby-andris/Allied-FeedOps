    **Part A: Fix fetch_search_terms() in google_ads_search_terms.py**

    The current implementation at lines ~593-620 of `fetch_search_terms()` fetches products by campaign (via `_fetch_campaign_products()`), then for each search term with a campaign_id, it uses `item_ids[0]` — the first (highest-impression) item — as the variant attribution. This is wrong.

    The correct behavior:
    - The Google Ads API cannot directly join search terms with specific variants (a documented limitation acknowledged in the legacy `get_terms_for_master_sku()` deprecation comment at line ~653).
    - However, we CAN improve attribution: instead of using `items_ids[0]` (the top item for the WHOLE campaign), we should:
      1. Keep all item_ids for the campaign in the result (already done — up to 10)
      2. In `save_search_terms_to_db()`, when there are multiple item_ids, save ONE row per item_id (not one row for item_ids[0] only), so each variant gets credited for the search term
      3. This allows per-variant search term data to surface on the Search Insights page

    Implementation in `fetch_search_terms()`:
    - The fix is in how we build the results list in the inner loop (lines ~604-620)
    - Instead of picking `gmc_offer_id = item_ids[0]` and creating ONE result entry, create an entry per item_id in the campaign (or keep the current single-entry structure but rely on `save_search_terms_to_db` to expand)
    - Simplest correct fix: in the results list, include ALL item_ids (keep current `item_ids[:10]`) and set `gmc_offer_id = None` (campaign-level attribution only, no false variant claim). The save function will store one row per query_text with null offer_id.
    - BUT: this loses variant-level data entirely. Better fix: expand in save_search_terms_to_db.

    **Recommended fix approach** (use judgment from diagnosis):

    Option A (if diagnosis says current data is bad because of wrong gmc_offer_id):
    In `fetch_search_terms()`, keep building results as-is but do NOT set `gmc_offer_id = item_ids[0]`. Instead set `gmc_offer_id = None` and keep `item_ids` (the full list). In `save_search_terms_to_db()`, for each search term with non-empty `item_ids` and null `gmc_offer_id`, expand into N rows — one per item_id — looking up variant info for each. This is the "per-variant expansion" approach.

    Option B (simpler, if diagnosis says data was just campaign-level):
    Keep `gmc_offer_id = item_ids[0]` in fetch (campaign's top item) but also emit additional result entries for each remaining item_id in the campaign. Each has the same search_term, same metrics, different gmc_offer_id. This populates one row per variant per search term per campaign.

    **Choose Option B** (unless diagnosis explicitly recommends otherwise). It's simpler and gives per-variant rows. The save function already deduplicates by (query_text, gmc_offer_id, period_start, period_end).

    Concrete changes to `fetch_search_terms()`:
    - In the results loop (around line 600-620), instead of appending one dict, append multiple dicts — one per item_id in the campaign:
      ```python
      for item_id in item_ids[:10]:  # up to 10 variants per campaign
          variant_info = self.get_variant_info(item_id)
          results.append({
              "search_term": search_term,
              "impressions": impressions,
              "clicks": clicks,
              # ... same metrics ...
              "campaign_id": campaign_id,
              "ad_group_id": ad_group_id,
              "item_ids": item_ids[:10],
              "gmc_offer_id": item_id,
              "master_sku": variant_info.get("master_sku"),
              "finish": variant_info.get("finish"),
              "finish_code": variant_info.get("finish_code"),
              "shopify_variant_id": variant_info.get("shopify_variant_id"),
          })
      ```
    - If item_ids is empty: emit one row with gmc_offer_id=None (unchanged from current).

    Also add `synced_at` to the result dict in `save_search_terms_to_db()`:
    - In the `deduped[key]` dict construction, add `"synced_at": datetime.utcnow().isoformat()` alongside `"fetched_at"`.

    **Part B: Fix collect_search_terms_batch() for delete-before-insert**

    The context decision requires: "Per-SKU delete right before re-inserting that SKU (not a full table wipe). Safe for resume: if job fails mid-way, only processed SKUs are cleared."

    Currently `collect_search_terms_batch()` in `workers.py` calls `save_search_terms_to_db()` which does an upsert. The upsert will update existing rows but won't delete rows that no longer exist in the new fetch (e.g., old wrong-variant rows).

    Fix in `collect_search_terms_batch()`:
    1. Before calling `save_search_terms_to_db()`, for each SKU in the batch that has validated_terms, delete existing search_queries rows for that master_sku:
    ```python
    from feedops.db.supabase_client import get_client
    supabase = get_client()

    # Per-SKU delete before re-insert (clean slate per context decision)
    skus_with_data = list({t.get("master_sku") for t in validated_terms if t.get("master_sku")})
    for sku in skus_with_data:
        logger.info(f"Deleting existing search_queries rows for {sku} before re-insert")
        supabase.table("search_queries").delete().eq("master_sku", sku).execute()
    ```
    2. Then call `save_search_terms_to_db()` as before.

    This pattern means:
    - If job fails after processing SKU A but before SKU B → SKU A has corrected data, SKU B has original data (distinguishable by synced_at: SKU A rows have synced_at, SKU B rows have NULL)
    - Resume-safe: re-running for SKU A will delete and re-insert again (idempotent)

    Also add the supabase import at top of the function if not already present (it's imported within the function scope currently from other places — add `get_client` usage directly in this function, following existing pattern in collect_performance_batch which already does `from feedops.db.supabase_client import get_client`).
