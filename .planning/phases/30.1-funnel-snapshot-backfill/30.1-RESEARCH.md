# Phase 30.1: Funnel Snapshot Backfill - Research

**Researched:** 2026-02-25
**Domain:** Google Ads GAQL historical queries + Supabase upsert + Python scripting
**Confidence:** HIGH

## Summary

Phase 30.1 backfills the `funnel_snapshots_daily` table with historical Google Ads data so the FunnelTrendCards component shows meaningful 7d vs prev-7d trend comparisons immediately, rather than waiting 14+ days for organic accumulation from the daily Cloud Scheduler job. Currently, only 1 day of data exists (2026-02-24, 142 rows).

The backfill is technically straightforward because: (1) `getLabelTierPerformance()` in `service.ts` already accepts arbitrary `startDate`/`endDate` parameters, (2) the underlying GAQL `search_term_view` query supports historical date ranges natively, (3) the `funnel_snapshots_daily` table uses `ON CONFLICT (snapshot_date, custom_label_0, tier) DO UPDATE` making re-runs idempotent, and (4) Google Ads API quota is at ~1.2% utilization with 14,813 requests of headroom per day.

The key decision is whether to build a Python script (per CLAUDE.md stack rules for scripts) or a TypeScript approach that reuses the existing `getLabelTierPerformance()` function directly. The GAQL queries live in TypeScript `service.ts`, so a Python script would need to duplicate the query logic. A one-time TypeScript script (run via `npx tsx`) or a temporary API endpoint is more pragmatic since it reuses proven code.

**Primary recommendation:** Create a temporary backfill API endpoint (`/api/funnel-snapshots/backfill`) that loops over a date range, calls `getLabelTierPerformance()` for each day, and upserts results. Run it once manually, then optionally delete the endpoint. This reuses 100% of the existing proven query and write logic.

### Pattern 1: Day-by-Day Backfill Loop
**What:** The backfill endpoint iterates over each date in the requested range, calls `getLabelTierPerformance({ startDate: date, endDate: date })` for each day, and upserts results to Supabase. Sequential execution avoids API rate limiting.
**When to use:** Always -- the GAQL `search_term_view` query aggregates metrics across the full date range, so a multi-day query would return totals, not per-day snapshots.
**Example:**
```typescript
// Source: capture/route.ts pattern + service.ts getLabelTierPerformance signature
for (const date of dateRange) {
  const result = await getLabelTierPerformance({
    startDate: date,
    endDate: date,
  })

  const rows = result.rows.map((row) => ({
    snapshot_date: date,
    custom_label_0: row.custom_label_0,
    tier: row.tier,
    impressions: row.impressions,
    clicks: row.clicks,
    cost_micros: row.cost_micros,
    conversions: row.conversions,
    conversions_value: row.conversions_value,
    roas: row.roas,
  }))

  if (rows.length > 0) {
    await supabase
      .from('funnel_snapshots_daily')
      .upsert(rows, { onConflict: 'snapshot_date,custom_label_0,tier' })
  }
}
```

### Pattern 2: Authentication and Safety
**What:** The backfill endpoint uses the same Bearer token auth as the capture endpoint (CRON_SECRET), preventing unauthorized execution. Since backfill is a one-time operation, additional safety measures include a maximum date range limit and progress logging.
**When to use:** Always.
**Example:**
```typescript
// Same auth pattern as capture/route.ts
const cronSecret = process.env.CRON_SECRET
const token = authHeader.replace(/^Bearer\s+/i, '')
if (token !== cronSecret) {
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
}

// Safety: limit max range to 90 days (table retention policy)
const maxDays = 90
if (dayCount > maxDays) {
  return NextResponse.json({ error: `Max ${maxDays} days` }, { status: 400 })
}
```

### Anti-Patterns to Avoid
- **Multi-day GAQL query expecting per-day breakdown:** `getLabelTierPerformance({ startDate: '2026-02-10', endDate: '2026-02-24' })` returns TOTALS for the entire range, NOT per-day rows. The GAQL query does not include `segments.date` in the SELECT, only in the WHERE clause. Must query one day at a time.
- **Parallel day queries:** Firing 30+ concurrent `getLabelTierPerformance()` calls would hit 210+ simultaneous GAQL queries (7 per call). Sequential execution is safer and still fast (~5-15 seconds per day).
- **Modifying service.ts:** Do NOT add `segments.date` to the existing GAQL query to enable multi-day breakdowns. This would change the live dashboard behavior.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| GAQL query for tier data | Duplicate Python queries | `getLabelTierPerformance()` from service.ts | Guarantees schema parity with daily capture |
| Date range iteration | Custom date math | Simple loop: `while (current <= end) { ... current.setDate(current.getDate() + 1) }` | Straightforward |
| Upsert logic | Manual INSERT/UPDATE | Supabase `.upsert()` with `onConflict` | Handles re-runs safely, matches capture endpoint |
| Row format mapping | New mapping logic | Copy exact mapping from capture/route.ts | Guarantees format parity |

**Key insight:** The backfill must produce rows identical to what the daily capture endpoint produces. Reusing the same function (`getLabelTierPerformance`) and the same mapping logic (from `capture/route.ts`) guarantees this.

## Common Pitfalls

### Pitfall 1: GAQL Aggregates Across Date Range (Not Per-Day)
**What goes wrong:** Calling `getLabelTierPerformance({ startDate: '2026-02-10', endDate: '2026-02-24' })` returns a single set of rows with summed metrics across all 15 days, not 15 separate daily snapshots.
**Why it happens:** The GAQL query in `fetchAdsContext()` (service.ts line 553-569) uses `segments.date BETWEEN '...' AND '...'` only in the WHERE clause. The SELECT clause does not include `segments.date`, so results are aggregated across the entire date range.
**How to avoid:** Always query one day at a time: `getLabelTierPerformance({ startDate: date, endDate: date })`.
**Warning signs:** Backfilled rows have suspiciously high metric values compared to daily capture rows.

### Pitfall 2: Vercel Function Timeout on Large Backfills
**What goes wrong:** A 30-day backfill means 30 sequential calls to `getLabelTierPerformance()`, each taking 5-15 seconds. That is 150-450 seconds total, far exceeding Vercel's 60-second function timeout (or 300-second for Pro).
**Why it happens:** Vercel serverless functions have strict timeout limits.
**How to avoid:** Two options: (A) Accept partial progress -- the endpoint processes as many days as possible within the timeout, and re-running covers remaining days (upsert is idempotent). (B) Run the backfill locally via `curl` against `localhost:3000` where there is no timeout. Option B is strongly recommended.
**Warning signs:** 504 Gateway Timeout responses after ~60 seconds.

### Pitfall 3: Google Ads Data Availability Window
**What goes wrong:** Requesting data too far back may return zeros or incomplete data.
**Why it happens:** Google Ads `search_term_view` retains data for a limited window. The exact retention period is not documented, but 90 days of search term data is generally available. Data older than that may be sparse or missing.
**How to avoid:** Target 30 days of backfill (safe margin within Google Ads data retention). The success criteria require 14 days minimum.
**Warning signs:** Rows for older dates have zero impressions across all labels/tiers.

### Pitfall 4: fetchAdsContext Caches Across Days
**What goes wrong:** `fetchAdsContext()` has a 2-minute in-memory cache keyed on `startDate:endDate`. In a sequential loop, each day gets a unique cache key, so this is NOT actually a problem. But if the loop runs fast enough, the 7 non-search-term queries (campaigns, ad groups, shared sets, etc.) are re-fetched for every day even though they are date-independent.
**Why it happens:** The cache key includes the date, so `2026-02-10:2026-02-10` and `2026-02-11:2026-02-11` are different keys.
**How to avoid:** Accept the overhead -- 7 queries per day x 30 days = 210 queries, well within the 15,000 daily limit. Optimization is not needed.
**Warning signs:** Slightly slower backfill than expected (~10-15 seconds per day instead of ~5 seconds).

## Code Examples

### Backfill Endpoint
```typescript
// dashboard/src/app/api/funnel-snapshots/backfill/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { getLabelTierPerformance } from '@/lib/shopping-funnel/service'
import { createAdminClient } from '@/lib/supabase/admin'

export async function POST(request: NextRequest) {
  // Auth check (same as capture)
  const cronSecret = process.env.CRON_SECRET
  if (!cronSecret) {
    return NextResponse.json({ error: 'CRON_SECRET not configured' }, { status: 401 })
  }
  const authHeader = request.headers.get('authorization') ?? ''
  const token = authHeader.replace(/^Bearer\s+/i, '')
  if (token !== cronSecret) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }

  // Parse date range from request body
  const body = await request.json()
  const { start_date, end_date } = body as { start_date: string; end_date: string }

  if (!start_date || !end_date) {
    return NextResponse.json({ error: 'start_date and end_date required' }, { status: 400 })
  }

  const supabase = createAdminClient()
  const results: Array<{ date: string; rows: number }> = []

  // Iterate day by day
  const current = new Date(start_date)
  const endDate = new Date(end_date)

  while (current <= endDate) {
    const dateStr = current.toISOString().split('T')[0]

    try {
      const result = await getLabelTierPerformance({
        startDate: dateStr,
        endDate: dateStr,
      })

      const rows = result.rows.map((row) => ({
        snapshot_date: dateStr,
        custom_label_0: row.custom_label_0,
        tier: row.tier,
        impressions: row.impressions,
        clicks: row.clicks,
        cost_micros: row.cost_micros,
        conversions: row.conversions,
        conversions_value: row.conversions_value,
        roas: row.roas,
      }))

      if (rows.length > 0) {
        const { error: upsertError } = await supabase
          .from('funnel_snapshots_daily')
          .upsert(rows, { onConflict: 'snapshot_date,custom_label_0,tier' })
        if (upsertError) {
          console.error(`[backfill] Upsert failed for ${dateStr}:`, upsertError.message)
        }
      }

      results.push({ date: dateStr, rows: rows.length })
      console.log(`[backfill] ${dateStr}: ${rows.length} rows`)
    } catch (err) {
      console.error(`[backfill] Error for ${dateStr}:`, err)
      results.push({ date: dateStr, rows: -1 })
    }

    current.setDate(current.getDate() + 1)
  }

  return NextResponse.json({
    total_days: results.length,
    total_rows: results.filter(r => r.rows > 0).reduce((sum, r) => sum + r.rows, 0),
    days: results,
  })
}
```

## Open Questions

1. **How far back should we backfill?**
   - What we know: Success criteria require 14 days minimum. Google Ads retains search_term_view data for at least 90 days.
   - What's unclear: Whether data quality degrades for older dates. 1 day of data (2026-02-24) already exists and shows 142 rows as expected.
   - Recommendation: Backfill 30 days (2026-01-25 to 2026-02-24). This provides 4 weeks of trend context and stays well within data retention limits. The 90-day retention policy on the table means we could go further, but 30 days provides enough for trend analysis.

2. **Should the backfill endpoint be deleted after use?**
   - What we know: It is a one-time operation. Leaving it deployed adds a minor attack surface (protected by CRON_SECRET, but still).
   - Recommendation: Keep it temporarily in case re-runs are needed (e.g., if data quality issues are found). Delete in Phase 31 schema cleanup.

3. **Vercel timeout: will 30 days complete in one request?**
   - What we know: Each day takes 5-15 seconds. 30 days = 150-450 seconds. Vercel Pro timeout is 300 seconds.
   - Recommendation: Run against localhost (no timeout). If Vercel deployment is needed, break into 10-day chunks. The upsert-on-conflict makes partial runs + re-runs safe.
