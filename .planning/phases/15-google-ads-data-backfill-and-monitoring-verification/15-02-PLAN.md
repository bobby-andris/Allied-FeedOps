# Key facts for this plan

## Backfill endpoint
POST https://feedops-pipeline-623866089882.us-east1.run.app/backfill/start

Request body (StartBackfillRequest):
```json
{
  "job_type": "performance_metrics",
  "skus": ["<list of all master_skus from variant_index>"],
  "config": {
    "batch_size": 10,
    "checkpoint_interval": 100,
    "days_lookback": 180
  }
}
```

Fields:
- `job_type`: must be "performance_metrics" (routes to collect_performance_batch worker)
- `skus`: list of master_sku strings — must fetch all distinct master_skus from variant_index first
- `config.batch_size`: 10 (validated optimal batch size from Phase 0 testing)
- `config.checkpoint_interval`: 100 (saves progress every 100 SKUs for resume capability)
- `config.days_lookback`: 180 (30-day pre-publish baseline uses 180-day Google Ads window)

## Status endpoint
GET https://feedops-pipeline-623866089882.us-east1.run.app/backfill/status/{job_id}

Response fields:
- `status`: "pending" | "running" | "completed" | "partial" | "failed"
- `total_items`: number of SKUs in the job
- `completed_items`: SKUs successfully processed
- `failed_items`: SKUs that failed (rate limits, no data, etc.)
- `eta_seconds`: estimated time remaining

## Concurrent job limit
The endpoint enforces max 3 concurrent jobs. Verify no other jobs are running before starting.
Check: GET /backfill/jobs?status=running

## How to get all 2,784 SKUs
Query Supabase for distinct master_skus:
```sql
SELECT DISTINCT master_sku FROM variant_index ORDER BY master_sku;
```
Use mcp__supabase__execute_sql — will return ~2,784 rows.
Extract the master_sku values into a JSON array for the request body.

## Resume capability
If the job fails or is partial:
POST /backfill/resume/{job_id}
The job restarts from its last checkpoint (every 100 SKUs), so retries are safe.

## Expected duration
Phase 0 testing: 7.1 minutes for 2,784 SKUs with batch size 10.
With rate limiting overhead and performance_metrics worker: expect 15-30 minutes.
Poll every 2 minutes.

## Pre-backfill baseline
- performance_baselines: 188 rows, 96 distinct master_skus

## Verification queries
```sql
SELECT COUNT(DISTINCT master_sku) as distinct_skus, COUNT(*) as total_rows
FROM performance_baselines;
```

## SKUs that may fail (expected)
- SKUs not in any active Google Ads campaign → no data returned → counted as "failed"
- SKUs with insufficient data volume → Google Ads returns zeros → still written (not failed)
- Rate limit errors → individual SKUs are retried within the batch
Expected: 80-95% success rate is acceptable (performance_metrics = "partial" status if <95%)
