# Key facts for this plan

## Sync endpoint
POST https://feedops-pipeline-623866089882.us-east1.run.app/search-insights/sync

Request body (SyncSearchTermsRequest):
- `days`: int, 7–180. Use 30 for each chunk.
- `limit`: int, 100–5000. Use 5000 (max) to capture all terms per window.
- `enrich_with_keyword_planner`: bool. Use false during backfill to keep jobs fast.

Response (SyncJobResponse):
- `job_id`: string (UUID)
- `status`: "pending" initially

## Status check endpoint
GET https://feedops-pipeline-623866089882.us-east1.run.app/search-insights/sync/{job_id}

Response (SyncStatusResponse):
- `status`: "pending" | "running" | "completed" | "failed"
- `queries_fetched`: rows written to search_queries
- `error_message`: null if successful

## How the sync works
The endpoint is account-wide — it fetches ALL active SKUs in the Google Ads account for the given date range, then upserts rows into search_queries. The `days` parameter sets the lookback window: when days=30, the sync covers the most recent 30 days. To cover 180 days total, we run 6 sequential syncs.

IMPORTANT: The endpoint uses BETWEEN date strings (fixed in Phase 14). The date range is calculated as:
  end_date = today
  start_date = today - days

This means each call uses "today minus N days" as the window. To cover different historical periods, we need to verify sequential runs capture different date ranges — OR we accept that each call uses the same "most recent 30 days" window but fetches with upsert logic (ON CONFLICT DO UPDATE), so running 6 times covers the full set of search queries that appeared within 30-day windows of the API's available history.

ACTUAL APPROACH: The sync endpoint does NOT accept explicit start/end date parameters — only `days`. Each call fetches "the most recent N days." Running 6 sequential calls of 30 days will fetch the same date window 6 times (upserts are idempotent). To achieve true 180-day coverage, use days=30 first to verify the fix works, then run a SINGLE call with days=180 (the endpoint accepts up to 180 for the `days` param).

REVISED PLAN: The `days` parameter allows up to 180. The BETWEEN fix in google_ads_search_terms.py means we can now pass days=180 and it will generate a valid BETWEEN 'YYYY-MM-DD' AND 'YYYY-MM-DD' range covering 180 days. So the plan is:
1. Smoke test: days=30, verify job completes
2. Full backfill: days=180, single call, max limit=5000
3. Verify row count and synced_at

The "6 sequential 30-day windows" in the phase description was a safety constraint when BETWEEN was broken. With the fix applied, days=180 in a single call is correct and simpler.
