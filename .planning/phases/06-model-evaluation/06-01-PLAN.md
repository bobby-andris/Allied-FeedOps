<task type="auto">
  <name>Task 1: Create SKU selection script and evaluation script</name>
  <files>scripts/select_eval_skus.py, scripts/run_model_evaluation.py</files>
  <action>
Create two Python scripts:

**scripts/select_eval_skus.py** — Queries Supabase for 15-20 diverse SKU candidates.
- Use `mcp__supabase__execute_sql` pattern OR direct Supabase client (stdlib urllib approach like verify_content_quality.py, using SUPABASE_URL + SUPABASE_KEY env vars).
- Query `product_catalog` joined with `generated_content` to find:
  - Category spread (different product types)
  - Single vs multi-SKU products (same product_id shared by multiple master_skus)
  - SKUs with existing `approved_content` (3-4 of them for reference comparison)
  - Collection variety
- Use one representative variant per master_sku (e.g., WHERE finish_code = 'ORB' or just DISTINCT ON master_sku).
- Output a markdown table with columns: master_sku, category, collection, is_multi_sku, has_approved_content, rationale.
- Print to stdout. User picks 10.
- Stdlib only (urllib + json + os). No external deps.

**scripts/run_model_evaluation.py** — Parameterized multi-model evaluation script.
- Uses argparse with:
  - `--skus` (space-separated list, required)
  - `--models` (default: gpt-5.2 claude-sonnet-4-6 claude-opus-4-6)
  - `--passes` (default: 3)
  - `--output-dir` (default: docs/evaluation)
  - `--platforms` (default: google,bing,shopify)
  - `--reasoning-effort` (default: high — matches GPT-02 locked decision)
- MODEL_CONFIGS maps model names to env var dicts:
  ```python
  MODEL_CONFIGS = {
      "gpt-5.2": {"FEEDOPS_PROVIDER": "openai", "FEEDOPS_OPENAI_MODEL": "gpt-5.2"},
      "claude-sonnet-4-6": {"FEEDOPS_PROVIDER": "claude", "FEEDOPS_CLAUDE_MODEL": "claude-sonnet-4-6"},
      "claude-opus-4-6": {"FEEDOPS_PROVIDER": "claude", "FEEDOPS_CLAUDE_MODEL": "claude-opus-4-6"},
  }
  ```
- For each SKU x model x pass:
  1. Save current env vars, set model env vars, get provider via `get_provider()`
  2. Load ParentSKU via `load_parent_sku_from_supabase(master_sku)`
  3. Call `generate_per_platform()` directly (bypasses HTTP endpoint and DB persistence)
  4. Extract per-platform metrics from the returned dict: `usage_by_platform`, `latency_by_platform`, `parse_by_platform`, `retry_by_platform`
  5. Calculate cost using per-model pricing table (PRICING dict from research)
  6. Restore env vars
  7. Sleep 2 seconds between calls (rate limit safety)
- Handle generation failures gracefully: log error, write row with error column filled, continue to next
- Use env var context manager pattern to prevent leakage:
  ```python
  @contextmanager
  def model_env(config: dict):
      saved = {k: os.environ.get(k) for k in config}
      os.environ.update(config)
      try:
          yield
      finally:
          for k, v in saved.items():
              if v is None:
                  os.environ.pop(k, None)
              else:
                  os.environ[k] = v
  ```
- Write all results to `{output_dir}/raw_results.csv` with fields from research CSV_FIELDS.
- Also extract content for each platform from the response dict keys: `{platform}_title`, `{platform}_description`.
- Measure consistency across 3 passes using `difflib.SequenceMatcher` (mean pairwise similarity per SKU x model x platform).
- Write consistency analysis to `{output_dir}/consistency_analysis.md`.
- Print progress to stdout: "Generating SKU {n}/10 model {model} pass {p}/3..."
- Print summary statistics at end: p50/p95 latency per model, avg cost per SKU per model, total cost.
- Script runs with: `PYTHONPATH=./src python scripts/run_model_evaluation.py --skus SKU1 SKU2 ...`
- Requires env vars: OPENAI_API_KEY, ANTHROPIC_API_KEY, SUPABASE_URL, SUPABASE_KEY (load from .env.vercel).

CRITICAL anti-patterns to avoid:
- Do NOT call /optimize-sku via HTTP — response does not expose per-platform content or token counts
- Do NOT write to generated_content table — generate_per_platform() called directly does NOT persist (persistence is in routes.py only)
- Do NOT forget to restore env vars between model runs
- Do NOT use reasoning_effort != "high" unless explicitly overridden — "high" is the locked default from Phase 4
